# MyFamily: поддержка по develop

Основной источник — `origin/develop`, commit `cbd4086dc5e30c8e5a77262e1c944cc1514d30d4` (последний доступный локально снимок). Рабочая копия MyFamily не переключалась, её изменения сохранены. Документы подготовлены по 26 Swift-файлам, пути и SHA-256 исходников зафиксированы в `support/myfamily/develop/provenance.json`. Это проверка исходников, а не запуск iOS-приложения или мониторинг production.

## Знания и контекст

| Раздел | Что знает ассистент | Учитываемый контекст |
| --- | --- | --- |
| Вход | VK ID, срок действия сессии, проверка семьи | Способ входа, этап, сессия |
| Семья | Создание, вступление, приглашения, удаление участника | Наличие семьи, familyId, роль owner/regular |
| Карта | Разрешения, фоновые обновления, домашняя точка, статусы | Разрешение геолокации выбранного устройства |
| Лента | Семейные публикации, лайки, комментарии, доступ по ссылке, кэш | Наличие семьи и исходная проблема тикета |
| Медиа | Фото, видео, аудио, проверка текста и изображений | Микрофон, камера, фото; результат проверки, если известен |
| Профиль | Имя, фамилия, фото, условия сохранения, выход из семьи | Состояние профиля, семейная роль |
| Pro | StoreKit, premiumstatus, pending, покупка и восстановление | Статус Pro и попытки покупки |

Восемь документов (37 фрагментов в текущем индексе) находятся в `support/myfamily/develop/knowledge/`. В RAG попадают эти документы; секреты, сырые настройки SDK, исходные профили и переписка не индексируются. `knowledgeRevision` в CRM должен совпадать со снимком всех документов, иначе запрос отклоняется до вызова модели. Изменение документов делает индекс устаревшим; изменение CRM читается при следующем MCP-вызове без переиндексации.

Демонстрационная CRM — `support/myfamily/develop/crm.demo.json`. Она содержит синтетические профили и события, без координат, токенов, действующих приглашений и платёжных данных. Backend MyFamily не подключён. Неизвестные структурированные поля отбрасываются Zod-схемой, включая вложенные поля семьи, Pro и разрешений.

Новый путь CRM изолирует тикеты develop от прежних SMS-тикетов: SQLite использует область данных по каноническому пути CRM. Старые обращения, удалённые тикеты и история остаются сохранены в своей области; они не удаляются и не перезаписываются. Стартовые тикеты импортируются один раз. Ответы создаются моделью после запроса пользователя; готовые ответы в JSON не зашиты.

## Демонстрация на видео

Откройте `http://127.0.0.1:5173/#support`. Локальная Qwen 9B выбрана по умолчанию. Для записи видео предпочтителен DeepSeek: он быстрее и прошёл полный набор сценариев. Облачная модель выбирается явно в шапке; запрос и синтетический контекст передаются этому провайдеру. Для чистой демонстрации нажмите «Создать тикет»; стартовые обращения также доступны для вопросов.

1. Выберите **Олега**, создайте обращение «Нет кнопки приглашения» с описанием «В разделе семьи не вижу кнопку добавления участника. Почему и что делать?». Покажите роль «Участник» в контексте. Ответ должен связать роль regular с правилом owner в документации и посоветовать обратиться к владельцу.
2. В том же тикете спросите: **«Если купить Pro, кнопка появится?»**. Ассистент должен объяснить, что Pro не меняет семейную роль, и сохранить ответ в этой переписке.
3. Переключитесь на **Анну**, у которой роль «Владелец», и спросите в её тикете: **«Как создать и скопировать приглашение?»**. Ответ должен объяснить доступный владельцу сценарий; покажите ссылки на документы и MCP.
4. У Олега откройте обращение о карте: **«Почему приложение не получает геолокацию моего устройства?»**. Контекст показывает запрет геолокации. Уточните: **«Это означает, что родственник тоже запретил геолокацию?»** — данных о чужом устройстве нет.
5. У **Ирины** спросите о неактивном Pro: pending означает ожидание подтверждения, а не доказанный успешный платёж. Дополнительный вопрос: **«Как работает восстановление покупок?»**.
6. Отметьте обращение решённым, обновите страницу и покажите сохранённую переписку. Удаление и восстановление доступны в шапке тикета и фильтре «Удалённые».

Другие вопросы: «Как вступить в семью?», «Почему публикация по ссылке недоступна?», «Как добавить аудио?», «Чем токсичный текст отличается от ошибки его проверки?», «Почему у владельца нет кнопки выхода из семьи?», «Как изменить имя и фото?», «Почему без сети видны старые публикации?».

## Запуск и проверка

```sh
npm run support:index
npm run dev
npm run test:support
npm run support:check
# Выбор отдельных реальных сценариев:
npm run support:check -- --cases family-member,map-denied,pro-pending
```

Проверка качества использует реальные локальные embeddings и Qwen 9B. Десять сценариев охватывают владельца и участника семьи, карту, отсутствие семьи, pending-покупку, микрофон, профиль, восстановление Pro, модерацию и отказ назвать неизвестный текущий инцидент. Ожидания проверяются после генерации и не передаются модели. Отчёт сохраняется после каждого сценария в `docs/day-33-myfamily-develop-local-results.json`, поле complete отличает завершённый прогон от промежуточного.

Автоматические проверки: 26/26 тестов поддержки, 141/141 общей регрессии поддержки, RAG, ассистента разработчика и code review. TypeScript и production-сборка проходят.

Реальный DeepSeek (`deepseek-v4-flash`) после отдельного разрешения на десять сценариев develop прошёл **10/10**, включая отказ назвать неизвестный текущий инцидент. Финальный повтор по уточнённым правилам тоже прошёл 10/10; время ответа — 4,9–14,2 секунды. Отчёт: [day-33-myfamily-develop-cloud-results.json](day-33-myfamily-develop-cloud-results.json).

Первый прогон Qwen 9B прошёл **9/10**: сценарий pending-покупки не выпустил неподтверждённый ответ из-за неверного выбора цитаты. Этот результат сохранён в `day-33-myfamily-develop-local-initial-results.json`. Заголовки без фактов исключены из доступных цитат. Для локального ответа по тикету введён обязательный contextClaim с выбором только MCP-доказательств; он затем проходит ту же смысловую проверку вместе с объяснением. Это не готовый ответ и не автоматическое добавление фактов сервером. Повтор проблемного сценария прошёл **1/1**, 88,0 секунды; отдельный отчёт `day-33-myfamily-develop-local-results.json` содержит selected=[pro-pending], а не новый полный прогон десяти сценариев.

При проверке уточнения о Pro локальная Qwen предложила неверный обход через удаление и повторное приглашение. Исходная пробная переписка сохранена в «Удалённых»; в FAQ теперь прямо сказано, что повторное вступление снова назначает regular и не даёт owner. Этот случай показывает ограничение модели и смысловой проверки: наличие цитат не гарантирует безошибочность каждого вывода. Для демонстрации рекомендуется DeepSeek, для использования локальной модели важные советы нужно сверять с источниками. Новые права и изменения данных ассистент самостоятельно не применяет.

`--cloud` явно включает DeepSeek и передачу подготовленной документации с синтетическим контекстом; наличие ключа само по себе не включает облако. Исторические отчёты MyFamily без develop относятся к раннему `main` и не доказывают качество нового набора. Описание предыдущего снимка и его результатов сохранено в [day-33-myfamily-main.md](day-33-myfamily-main.md).

## Границы ответов

Ассистент не выдумывает серверные ACL из клиентского UI, срок действия приглашения, тарифную сетку и сроки возврата. Нет данных о текущем Firebase-инциденте — обращение переходит в «Нужен оператор». Подтверждение каждой рекомендации требует цитаты документа, факта выбранного аккаунта — MCP. Предыдущие ответы модели не становятся доказательствами. Все операции создания, уточнения, статусов, удаления и восстановления выполняет приложение через MCP; модель не получает инструменты изменения семьи, Pro или настроек устройства.

Ошибок браузерной консоли в финальной проверке нет.
