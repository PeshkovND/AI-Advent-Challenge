# День 32. Автоматизация ревью кода

## Результат

Добавлен GitHub Action `.github/workflows/ai-code-review.yml`. Он получает изменения PR, извлекает релевантные фрагменты документации и кода, вызывает существующий клиент модели и публикует текстовое AI-ревью. В отчёте три раздела: потенциальные баги, архитектурные проблемы, рекомендации. Пустые категории остаются пустыми: модель не обязана придумывать замечания.

Ветка реализации — `day-32`, создана от `day-31`.

## План и реализация

1. **Получение PR-контекста.** `server/code-review-context.ts` разрешает base/head в SHA и находит merge-base. `git diff merge-base head` возвращает статусы, пути и hunks. Содержимое файлов читается из Git blobs, для удалённых файлов — из merge-base. Состояние рабочей папки не влияет на анализ. Переименование представлено удалением старого и добавлением нового файла.
2. **RAG по документации и коду.** Из merge-base собирается корпус отслеживаемых текстовых файлов. Переиспользованы `documentFromText` и `chunkDocuments` из `rag-indexer.ts`, а также фильтр `publicProjectPath`. Для каждого файла отдельный TF-IDF-поиск выбирает до двух фрагментов документации и до двух фрагментов кода. Это лексический RAG: индекс строится в памяти за запуск, без SQLite, Ollama и embedding-модели на GitHub runner. Изменённый код head передаётся отдельно как diff и содержимое файла. Если по одной из категорий нет совпадений, контекст не заполняется нерелевантными фрагментами.
3. **Ревью.** `server/code-review.ts` реализует `CodeReviewAssistant`. Он использует общий `modelClient` из `local-rag-service.ts`, поэтому доступны существующий DeepSeek и локальная Ollama. Модель получает отдельный запрос на каждый файл и возвращает структурированные замечания с категорией, серьёзностью, местом, объяснением, исправлением и цитатами.
4. **Проверка и вывод.** Zod проверяет JSON; код проверяет путь, сторону LEFT/RIGHT, реальную строку переданного hunk и дословные цитаты. Для каждого замечания обязательна цитата из строки diff. При невалидном ответе — одна повторная попытка. Сбой модели не превращается в успешное ревью без замечаний: в отчёте остаётся ошибка, CLI завершается с кодом 1. Семантика замечаний не проверяется отдельной LLM и требует проверки разработчиком.
5. **Пайплайн.** Action запускается на opened/synchronize/reopened/ready_for_review, пропускает draft PR, обновляет один комментарий и сохраняет Markdown/JSON в артефакте `ai-code-review`. Устаревший результат не публикуется, если HEAD или base PR изменились за время анализа. Отчёт также доступен в Job Summary. Комментарий ограничен 55 КБ; полный отчёт сохраняется в артефакте.

Это отдельный сценарий существующей архитектуры ассистента разработчика. `/help`, его MCP-инструменты, маршруты, индексы и UI не изменены. Диалоговый `AgentService` не запускается в CI: история диалога и инструментальные действия ревью не нужны. Переиспользуются общие модельный клиент, чанкер и граница доступа к публичным путям проекта.

## Подключение GitHub

1. Добавить изменения дня 32 в default branch репозитория (сейчас `main`). Workflow и reviewer должны уже существовать в default branch; первый PR, устанавливающий эту возможность, не может проверить себя этим пайплайном.
2. Открыть **Settings → Secrets and variables → Actions → New repository secret** и добавить `DEEPSEEK_API_KEY`. Локальная `.env` не передаётся в GitHub Actions.
3. При необходимости добавить repository variable `AI_REVIEW_MODEL`. По умолчанию используется существующая в проекте `deepseek-v4-flash`.
4. Убедиться, что GitHub Actions разрешены и политика репозитория допускает `contents: read` и `pull-requests: write` для workflow. Параметр разрешения создавать и одобрять PR не нужен: публикуется обычный комментарий.
5. Открыть обычный PR или добавить новый commit в открытый PR. Дождаться **Actions → AI code review**. Проверить комментарий, Job Summary и артефакт.

Используется `pull_request_target`, чтобы выполнять доверенный reviewer и публиковать результат также для fork PR. Checkout указывает на **SHA default branch из `github.sha`**, в контексте которой запускается `pull_request_target`. Base/head PR используются только для чтения Git-контекста. Head загружается через `git fetch` и читается только как Git-объекты; код, workflow, зависимости и скрипты из PR не исполняются. `npm ci --ignore-scripts` устанавливает зависимости доверенной default branch. Ключ модели передаётся только шагам проверки конфигурации и ревью; GitHub token — шагам загрузки объектов и публикации. Модель не имеет инструментов и токен GitHub не получает. Данные PR и RAG объявлены недоверенными в system prompt. Эти требования соответствуют [рекомендациям GitHub по pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

PR-код и найденные фрагменты отправляются в DeepSeek; CI использует облачного провайдера. Для локального анализа есть `--local`. Артефакты содержат найденные фрагменты проекта и хранятся 7 дней.

## Локальный запуск

Node.js 24+, установленные зависимости и доступные локальные Git refs:

```bash
npm ci

# Только собрать diff, содержимое файлов и RAG, без модели и ключа:
npm run review:pr -- --base main --head HEAD --prepare-only

# Облачное ревью, DEEPSEEK_API_KEY берётся из существующей .env:
npm run review:pr -- --base main --head HEAD

# Локальная генерация через существующую Ollama:
npm run review:pr -- --base main --head HEAD --local

# Внешний Git-репозиторий, без регистрации в UI:
npm run review:pr -- --root /path/to/project --base main --head feature --output data/external-review

# Демо с намеренной арифметической ошибкой во временном репозитории:
npm run review:demo
# Или npm run review:demo -- --local
```

`main`, `feature` и `HEAD` в примерах — уже существующие локальные refs. Если удалённый PR ещё не загружен, сначала нужен обычный `git fetch`. Reviewer сам не выполняет сетевые запросы к Git. Анализируются **коммиты**, поэтому незакоммиченные правки не попадут в diff.

Результаты по умолчанию:

- `data/code-review/context.json` — подготовка с `--prepare-only`.
- `data/code-review/review.md` — полный текст ревью.
- `data/code-review/review.json` — замечания, RAG-источники и покрытие.
- `data/code-review/comment.md` — версия комментария с ограничением размера.
- `data/code-review-demo/` — результат демо. Временный Git-репозиторий удаляется после проверки.

CLI принимает `--base`, `--head`, `--root`, `--output`, `--local`, `--prepare-only`. Таймаут анализа — 12 минут; Action ограничен 20 минутами. Если ключ CI не настроен, шаг завершается явной ошибкой конфигурации, ревью не имитируется.

## Ограничения покрытия

- До 30 файлов PR за запуск. Лимиты централизованы в `reviewLimits`.
- До 10 000 байт diff и 4 000 байт содержимого на файл. Diff обрезается только по полным строкам. Усечение обозначается в отчёте.
- Для чтения допускаются обычные текстовые Git blobs до 128 000 байт. Симлинки, submodules, бинарные файлы, lock-файлы и неподдерживаемые форматы пропускаются с причиной.
- RAG-корпус ограничен 400 документами/файлами и 4 МБ. README и документация имеют приоритет. `.env`, скрытые каталоги, `data`, сборки, пути с именами credentials/secrets и ключи исключаются общим фильтром. Исключение для `.github/workflows/*.yml` позволяет анализировать workflow, сохраняя фильтрацию имён с секретами.
- Поиск использует документацию и код merge-base. Совместные изменения в нескольких файлах видны как отдельные diff; полная новая версия всех зависимостей одновременно модели не передаётся. Лексический поиск может пропустить смысловую связь с другими именами.
- Статус `complete` означает завершение анализа переданного объёма, `partial` — пропуски/усечение/ошибки части файлов, `failed` — не получено ревью ни одного выбранного файла. Наличие замечаний само по себе не делает Action красным: это консультативное ревью, без автоматического approve/request changes.
- Проверка цитат доказывает наличие текста в источнике, а не корректность вывода модели. Reviewer не запускает тесты и не заменяет разработчика.
