# День 28 — локальная LLM + RAG

Ветка day-28 добавляет **Локальный RAG**: сравнительную страницу по образцу раздела RAG с метриками скорости.

## Общий контрольный набор

Страница использует те же **11 вопросов**, ожидаемые ответы, источники и контрольные фрагменты из src/rag-demo-config.ts, что и раздел RAG. Для демонстрации оставлен только **улучшенный RAG**: structured, 10 кандидатов, rewrite, реранкинг, порог 2/3, top 4, цитаты и проверка.

Конфигурация берётся из общей функции demoAgentConfig('improved', indexRunId), а candidateTopK для локального сравнения переопределяется на 10. Ожидаемые ответы используются только для отображения и контроля, в промпт они не передаются. Остальные режимы исходной страницы RAG остаются доступны в своём разделе.

## Поиск и модель

Используется существующий SQLite-индекс Недели 6: 57 документов, 958 чанков, embedding nomic-embed-text-v2-moe, 768 измерений, ID d7864665-db3b-43cf-9c71-bb2e30365369 от 1 октября. Индекс — снимок корпуса на дату создания, автоматически не пересобирается. Эмбеддинги вопроса и cosine search выполняются локально.

Генерация: qwen3.5:4b через Ollama, temperature 0, reasoning выключен, контекст 32768, максимальный ответ 4096. Каждый вопрос независим. Индекс закрепляется на весь прогон, ответ с другим ID отклоняется.

В локальном режиме rewrite, реранкинг и проверка утверждений также выполняются Qwen. Оцениваются все найденные кандидаты (до 10 в улучшенном режиме этой страницы): если промпт реранкинга превышает консервативный бюджет контекста (UTF-8 байты плюс запас), кандидаты оцениваются частями, затем общий валидатор проверяет ID и покрытие. Отбор top 4 и порог релевантности не меняются. Обоснование оценки ограничено 60 символами; промпт просит 1–5 слов. В исходном разделе RAG остаётся 20 кандидатов. Обе колонки локального сравнения используют один и тот же сокращённый retrieval. Контекст 32768 и keep_alive=60s сохранены.

Локальный реранкер возвращает объект с отдельным обязательным ключом для каждого фрагмента (c1, c2 и т.д.). Сервер сопоставляет ключи с исходными chunkId; модель не копирует длинные ID. Проверяются полное покрытие, оценки 0–3 и непустые обоснования, без подстановки искусственных оценок.

Для локальной генерации сервер формирует каталог дословных доказательств (абзацы и ограниченные окна длинного текста, 12–1200 символов). Модель возвращает утверждения и короткие evidenceIds из JSON-схемы Ollama. Сервер сопоставляет ID с исходным chunkId и точным текстом; модель не копирует цитаты. Дословность и смысл затем проверяются существующим grounding/verifier. Это предотвращает технические ошибки копирования Markdown и пробелов, но не гарантирует смысловую правильность утверждений.

Первоначальный unknown при найденных доказательствах перепроверяется один раз. При исправлении после verifier модель получает предыдущий ответ в формате evidenceIds и конкретное замечание. Ответ не принуждается, ожидаемые ответы не передаются модели.

Для локального клиента включено сохранение проверенной части: после двух попыток показываются только утверждения с дословными цитатами и положительным решением verifier. Ответ явно помечается частичным; неподтверждённые утверждения и ссылки исключаются. Если положительно проверенных утверждений нет, сохраняется отказ. Техническая ошибка verifier не скрывается частичным результатом. Причины «модель не сформировала ответ» и «ответ отклонён проверкой» не описываются как доказанное отсутствие информации в документах.

Облачный клиент и исходные агенты сохраняют прежний режим полной проверки; обе модели используют одни найденные источники. Это сравнение клиентских реализаций пайплайна, а не изолированный тест мощности моделей. [Structured outputs Ollama](https://docs.ollama.com/capabilities/structured-outputs).

## Страница

В каждой карточке ожидаемый результат и источники находятся сверху; ниже только две колонки: **улучшенный RAG с локальной моделью** и **улучшенный RAG с облачной моделью**. Под полученным ответом показана одна строка времени.

Кнопка **Получить ответы на все 11 вопросов** запускает только улучшенный режим. Каждый результат сохраняется сразу; ошибка одного вопроса не останавливает остальные. При загрузке прежних отчётов отображаются и экспортируются только результаты improved.

Облачный ответ появляется при включённом сравнении с DeepSeek. Без сравнения работает только локальная модель, а облачная колонка показывает подсказку. Retrieval для пары выполняется один раз, включая локальные rewrite/реранкинг; обе модели получают один набор источников. В DeepSeek отправляются вопросы, найденные фрагменты и утверждения для проверки. По умолчанию облако выключено.

Доступны остановка, очистка результатов, экспорт JSON, загрузка CLI-отчёта и восстановление из localStorage. Старая трёхвопросная оценка не смешивается с новым набором: отчёты имеют version=2 и отдельные имена.

## Скорость

Под каждым полученным ответом отображается одна строка: **Время ответа: … с**. Это полное время поиска, генерации и проверки цитат, включая rewrite/реранкинг улучшенного режима. Общий поиск учитывается у обеих моделей; ожидание выполнения другой модели не добавляется.

Отдельной таблицы скорости и подробных метрик на странице нет. Смысл цитат проверяет сама модель; время ответа не является оценкой качества.

## Запуск

При готовом индексе:

```bash
ollama pull qwen3.5:4b
ollama pull nomic-embed-text-v2-moe
# Если Ollama не запущена как сервис:
ollama serve
# В другом терминале:
npm run dev
```

Для production: npm start. Готовая сборка сейчас на http://127.0.0.1:8797/. Откройте **Локальный RAG**. При отсутствии индекса: npm run rag:index.

Параметры .env: OLLAMA_BASE_URL=http://127.0.0.1:11434, OLLAMA_CHAT_MODEL=qwen3.5:4b, OLLAMA_CHAT_CONTEXT=32768, OLLAMA_CHAT_MAX_TOKENS=4096. Адрес Ollama допускает только loopback; embedding-модель берётся из метаданных индекса.

Контрольный прогон при API на порту 8787:

```bash
npm run rag:local:evaluate
npm run rag:local:evaluate -- --cloud
```

Для другого порта задайте LOCAL_RAG_APP_URL. CLI выполняет те же 11 вопросов только в улучшенном режиме. Сохраняет после каждого результата data/day-28-rag-comparison.json или data/day-28-rag-comparison-cloud.json. Ключ требуется только с --cloud; технические ошибки дают ненулевой код завершения.

API: GET /api/local-rag/status, GET /api/local-rag/report, POST /api/local-rag/compare. Тело POST: { question, mode, indexRunId, includeCloud: false }. Режимы without/structured/fixed/improved. Один запрос одновременно (второй получает 409), общий таймаут 15 минут, один LLM-вызов до 5 минут. Разрыв подключения отменяет upstream. Облачного fallback нет.

## Реальная диагностическая проверка

Проверен запуск общего набора и остановка из браузера. Длительный диагностический прогон остановлен после обнаружения ошибок: у первого вопроса structured дал цитируемый ответ за 8,04 с, fixed не прошёл проверку дословной цитаты. Затем схема локального реранкинга уточнена: ID, оценки 0–3 и короткие обоснования ограничены форматом Ollama. Финальная проверка улучшенного режима на вопросе 9 завершилась за 80,63 с без технической ошибки, но ответом «Не знаю». Реранкинг применён, все кандидаты оценены в первой попытке; это демонстрирует работу пайплайна, а не правильность отказа. Полный новый прогон всех 44 режимов не заявляется как выполненный.

## Проверка исправления реранкинга, 10 октября

Первый вопрос (scheduler.sqlite и получение задачи worker) через локальный HTTP API завершился без технической ошибки: оценены 20/20 кандидатов, одна попытка реранкинга, 4 выбранных источника, status=answered, проверка цитат passed. Полное время 176,388 с, реранкинг 68,928 с; генерация потребовала двух попыток. Это проверка одного вопроса, не результат полного прогона всех 11. Автоматические проверки локального RAG, retrieval и grounding: 42/42. Проверка смысла выполнена самой моделью и не заменяет ручную оценку.

## Проверка генерации цитат, 10 октября

После перехода локального клиента на evidenceIds выполнены три реальные локальные проверки с прежним индексом и улучшенным режимом. Вопрос 2 о пропущенных запусках получил подтверждённый ответ за 53,169 с; вопрос 3 о слоях памяти — за 61,245 с. Для обоих verification=passed, все цитаты дословно подставлены из найденных фрагментов. Redis (вопрос 11) — unknown/weak-context, источники пусты, 78,185 с: ответы без доказательств не принуждаются. Ожидаемые ответы не передавались модели. Остальные вопросы после этой правки не прогонялись. Автоматические проверки: 49/49, typecheck успешен. Время относится к этим конкретным запускам и не является гарантией скорости.

## Проверка частичного ответа

Первый вопрос воспроизведён с трассировкой: verifier подтвердил содержимое SQLite, отклонил составное утверждение о worker, повторная генерация вернула unknown. До исправления это уничтожало подтверждённый факт и ошибочно сообщало о нехватке сведений. После исправления полный локальный пайплайн вернул answered/partial с одним проверенным утверждением за 105,439 с. Детали получения задачи worker в этом запуске не подтверждены. Генерация вопросов 2 и 3 повторно проверена с их прежними найденными источниками: answered, verifier passed; эти проверки не включали повторный retrieval. Автоматические проверки: 52/52, typecheck успешен. Остальные вопросы после этой правки не прогонялись.

## Ускорение локального сравнения, 10 октября

Для страницы локального сравнения candidateTopK уменьшен с 20 до 10; topK=4, порог 2/3, контекст 32768, think=false и keep_alive=60s сохранены. Обоснования реранкера ограничены JSON-схемой до 60 символов, промпт просит 1–5 слов. Общая конфигурация исходного раздела RAG остаётся с 20 кандидатами.

Выполнен полный локальный прогон тех же 11 вопросов без облачных вызовов. В первом прогоне вопросы 6 и 8 выявили ошибки JSON проверяющей модели: лишнее поле и неполный/повторный набор ID. Для локального verifier введена схема с обязательным ключом на каждое утверждение; сервер переводит результат в прежний формат, сохраняя строгую проверку supported и reason. Семантические правила проверки и облачный клиент не менялись.

После исправления отдельно повторены вопросы 2, 6 и 8 с полным retrieval. Итоговый отчёт содержит 11 результатов с этими повторными запусками; это не второй полный прогон всех 11 после изменения схемы. Первоначальный отчёт сохранён отдельно как day-28-fast-rag-initial.json. В итоговом отчёте нет технических ошибок: 9 answered, включая partial на вопросе 6; вопрос 11 правильно отказался из-за отсутствия Redis в корпусе. Вопрос 2 дважды дал ложный unknown, хотя нужный контрольный фрагмент найден. Это не следует считать корректным ответом или успешным улучшением качества.

Все 15 контрольных фрагментов для 10 вопросов присутствуют среди выбранных источников; Redis оставил пустые источники. Это проверка retrieval, а не полноты и правильности каждого ответа. Проверяющий — та же небольшая модель, и его passed не заменяет ручную проверку.

Первый вопрос: 51,642 с вместо 105,439 с в предыдущем диагностическом запуске; реранкинг 25,485 с вместо 70,144 с. Вопрос 3: 46,965 с вместо 61,245 с. Redis: 27,480 с вместо 78,185 с. Замеры выполнены в разное время и не являются строгим парным бенчмарком. Среднее итоговых 11 запросов 40,06 с, медиана 41,80 с, средний реранкинг 20,50 с; среднее включает частичный ответ и оба unknown и не характеризует качество.
