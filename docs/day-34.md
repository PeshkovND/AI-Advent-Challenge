# День 34 — кодинг-ассистент для файлов проекта

Развивает ассистента дня 31 в том же разделе приложения, с тем же выбором локальной папки и провайдеров. Файловый режим работает напрямую с текущими исходниками, без индексации. Режим «Документация · RAG» и `/help` сохраняют прежний поиск с проверкой цитат.

## Соответствие заданию

| Требование | Реализация и проверка |
| --- | --- |
| Читать файлы проекта | `read_file`: содержимое актуальных Swift/TS/Markdown и других разрешённых текстовых файлов; реальные результаты в журнале задачи |
| Искать по нескольким файлам | `list_files` и буквальный `search_files`: пути, строки, совпадения, общее количество, пагинация и явные ограничения |
| Анализировать содержимое | Модель выбирает инструменты в цикле по цели, сопоставляет определения, вызовы и документацию |
| Создавать и менять файлы | `write_file` создаёт/заменяет полный файл; `replace_text` меняет единственное точное вхождение. Перед правкой существующего файла обязательно успешное чтение |
| Инициировать файловые действия самостоятельно | Первый список собирает приложение, дальнейшие поиск, чтение и редактирование выбирает модель; в пользовательском запросе достаточно цели |
| Минимум два сценария | Поиск определений/использований AuthService и обновление документации авторизации по коду MyFamily. Второй сценарий также создаёт новое руководство и diff |
| Работать минимум с 2–3 файлами | Приёмочный прогон требует минимум три прочитанных файла в каждом из двух сценариев; во втором три изменения: существующий справочник API, новое руководство и README |
| Сохранённые изменения или diff | Unified diff доступен в UI и CLI, скачивается как patch; применение сохраняет файлы, проверив исходное содержимое |
| Воспроизводимость | `npm run test:developer` без модели; `npm run developer:files:check -- --project ID` с локальной моделью на отдельной копии проекта. Повтор той же цели после применения должен давать нулевой diff |

## Как пользоваться

1. Запустите `npm run dev`, откройте **Ассистент разработчика** → **Открыть папку** → MyFamily.
2. Выберите Ollama либо DeepSeek. Для Ollama нужны запущенный локальный сервис и генеративная модель; embedding-модель для файловых задач не используется. Для DeepSeek нужен `DEEPSEEK_API_KEY`.
3. Задайте цель, например: «Найди определения и все использования AuthService. Объясни поток авторизации со ссылками на файлы и строки».
4. Для изменений: «Сверь документацию клиентского API с реализацией авторизации и обнови расхождения». Ассистент сам определит пути и подготовит diff.
5. Просмотрите действия и diff. Нажмите **Применить изменения**; либо **Скачать diff**, чтобы сохранить patch. Обновление статуса читает сохранённую серверную задачу.
6. Уточнение в той же беседе учитывает предыдущую цель и результат. Неприменённые изменения переносятся в виртуальный набор новой задачи, если исходники всё ещё совпадают. Применённые файлы перечитываются. **Новая беседа** сбрасывает этот контекст.

CLI использует тот же сервис:

```bash
npm run developer:cli -- --local --project myfamily 'Найди все использования AuthService и объясни его роль'
npm run developer:cli -- --local --project myfamily 'Дополни документацию авторизации по реальному коду и свяжи документы ссылками'
npm run developer:cli -- --project myfamily --apply 00000000-0000-4000-8000-000000000000
```

В последней команде замените UUID на ID полученной задачи. Применение не вызывает модель. Интерактивный CLI сохраняет контекст предыдущей задачи в процессе; `/help <вопрос>` вызывает RAG, `/index` обновляет индекс документации, `/exit` завершает CLI. После правок документации прежний RAG-индекс закономерно становится устаревшим.

## Архитектура

`server/coding-assistant.ts` реализует ограниченный цикл JSON-действий модели поверх общего транспорта `modelClient`. Контракт действий валидирует Zod, а локальная Ollama получает также JSON Schema для принудительного формата генерации; ошибку инструмента модель получает как данные и может исправить. Реальные операции выполняет `server/coding-files.ts` через файловые API Node и фиксированные вызовы Git для списка файлов и формирования diff. Это доступный tooling по условию задания; отдельный MCP для записи не требуется. MCP дня 31 продолжает обслуживать Git-контекст RAG-режима.

Перед выдачей результата отдельный вызов модели проверяет ответ и правки по цели и прочитанным исходникам (`review_changes`), в том числе для задачи без изменений. `goalChecks` содержит проверку каждого обязательного результата исходной цели; любой невыполненный пункт отклоняет даже положительный общий verdict. Исходники кода имеют приоритет в ограниченном контексте ревью; количество пропущенных источников отражается в receipt. Конкретные замечания возвращаются автору для исправления ответа/файлов и повторного просмотра diff, до четырёх проверок и двух повторов при ошибке формата. Если проверка не пройдена, результат не выдаётся как готовая задача и файлы проекта не меняются. Это дополнительная модельная проверка, а не гарантия корректности или замена тестам проекта.

Файловая система представляет виртуальный набор изменений поверх текущего проекта. После `write_file`/`replace_text` следующие чтения видят подготовленное содержимое, а реальные файлы остаются прежними. Перед завершением модель должна получить все страницы `get_diff`. История инструментов содержит настоящие результаты, а не сгенерированные receipts. `checkpoint` — явно обозначенная рабочая заметка модели с установленными фактами и оставшимися действиями; она не выдаётся за результат файлового инструмента. Заметка сохраняется между шагами. Одинаковые успешные результаты не дублируются в контексте. Старые наблюдения при исчерпании бюджета явно отмечаются как пропущенные. После шести исследовательских шагов повторные одинаковые чтения/поиски отклоняются, чтобы модель переходила к результату; новый необходимый файл ещё можно прочитать.

Финальная задача сохраняется в `data/coding-runs/<uuid>.json` для текущего проекта или `data/developer-projects/<hash-root>/coding-runs/` для внешнего. В записи находятся корень, цель, модель, прочитанные оригиналы, действия, исходное/новое содержимое и diff. Клиент передаёт на применение только ID задачи, а сервер загружает собственный снимок. Нельзя подставить корень или изменённый diff в apply-запрос. Применение повторно проверяет все прочитанные источники и все изменяемые файлы. При конфликте возвращается 409 до первой записи. Повторное применение сохранённой задачи не переписывает файлы.

Запись каждого файла выполняется через временный файл в том же каталоге и rename, с сохранением Unix permissions существующего файла. При обычной ошибке записи уже записанные файлы откатываются, если не обнаружено стороннее изменение. Ошибка отката явно называет файлы для ручной проверки. Это не транзакционная файловая система: аварийное завершение процесса/компьютера между записями может оставить часть изменений, поэтому сохраняемый patch и оригиналы важны для восстановления. Git add/commit не выполняются.

## API

Все маршруты находятся под `/api/developer`, используют существующий реестр `projectId` и loopback-проверку Host/Origin:

- `POST /tasks`: `{projectId?, goal, provider?: "local" | "cloud", previousRunId?}` → `CodingRun` со статусом `preview` или `completed`.
- `GET /tasks/:id?projectId=ID`: сохранить/восстановить просмотр результата задачи.
- `POST /tasks/:id/apply`: `{projectId?}` → та же задача со статусом `applied`.

С заголовком `Accept: text/event-stream` создание задачи возвращает SSE: `step` с названием операции/путём/ошибкой, затем `result` с полной задачей либо `error`. Веб-интерфейс использует этот режим и показывает действия во время выполнения. Без заголовка сохраняется обычный JSON-контракт. Для SSE после начала потока ошибки передаются событием, а не сменой HTTP-статуса.

Ошибки: 400 — входной контракт/путь; 403 — чужой Host/Origin; 404 — проект/задача не найдены; 409 — занят/конфликт; 422 — исчерпаны шаги; 502 — ошибка модели. Активный запрос отменяется при закрытии соединения или по лимиту 10 минут. До применения отмена/ошибка/исчерпание шагов не меняют файлы проекта. Если ответ apply прервался, обновите статус: синхронная запись могла успеть завершиться.

## Границы

- Один корень выбранного проекта; абсолютные пути, `..`, symlink, скрытые/служебные пути и имена секретов исключены. Git-список учитывает новые файлы и `.gitignore`. Без Git работает рекурсивный список с теми же исключениями каталогов.
- Только обычные UTF-8 текстовые файлы поддерживаемых расширений. Бинарные ресурсы, удаление и перемещение файлов, произвольные shell-команды, сборка и запуск тестов проекта пока не поддерживаются. Это первая версия кодинг-ассистента, а не полный аналог Codex/Claude Code.
- Файл на диске до 64 КиБ; полное чтение моделью до 14 КБ. Большие файлы доступны для поиска, но не для правки. До 12 изменённых файлов и 256 КиБ новых текстов за задачу. До 32 ответов модели; до шести действий за ответ. Поиск сканирует до 8 МиБ текста; `scanLimited` и `truncated` запрещают считать такой результат полным. Большой набор правок, не помещающийся в контекст независимой проверки, нужно разделить на несколько задач.
- `DEVELOPER_CODING_CONTEXT` задаёт отдельный консервативный бюджет (32768–131072, по умолчанию 65536), оставляя прежние RAG-настройки неизменными. `OLLAMA_CHAT_MODEL` выбирает локальную модель. Качество анализа зависит от модели; JSON-контракт и реальные receipts не заменяют семантическое ревью изменений.
- Выбранное содержимое файлов в облачном режиме уходит в DeepSeek; локальный режим обращается только к loopback Ollama. Файлы проекта и результаты инструментов считаются недоверенными данными, инструкции из них не должны менять цель пользователя.

## Проверка

```bash
npm run test:developer
npm run typecheck
npm run build
OLLAMA_CHAT_MODEL=qwen3.5:9b npm run developer:files:check -- --project myfamily
```

Зарегистрируйте проект через UI или `data/developer-projects.json` (образец в `developer-projects.example.json`). Для UI ID имеет вид `p-<hash>`; замените `myfamily` на ваш ID. Живая проверка создаёт отдельный текстовый checkout в `data/day-34-check/run-*/project`, выполняет поиск использований, готовит документацию, проверяет patch командой `git apply --check`, применяет изменения и повторяет ту же цель. Отчёт — `data/day-34-check/latest-<projectId>-local.json`, patch — рядом с тестовым checkout. Оригинальная папка MyFamily этим прогоном не меняется.

Автотесты покрывают поиск/чтение нескольких файлов, создание и изменение, валидность patch, применение после перезапуска сервиса, отсутствие записей до применения, конфликты исходников и назначений, повторное применение, пагинацию, symlink/секреты/бинарные файлы, ошибки инструментов, отмену и HTTP-контракты. Результаты живого прогона фиксируются отдельно; успешность iOS-сборки из них не следует.
