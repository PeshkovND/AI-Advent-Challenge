# День 23 — rewrite, реранкинг и фильтрация

В Day 24 четвёртый режим общей страницы дополнен обязательными цитатами и проверкой утверждений; см. [day-24.md](day-24.md). Ниже описаны исходная реализация и контрольные результаты Day 23.

RAG остаётся частью обычного агента: создание через `POST /api/agents`, конфигурация через `PUT /api/agents/:id`, запрос через стандартные `/run` и `/stream`. Отдельного endpoint генерации для демонстрации нет. Day 22 продолжает работать без rewrite и реранкинга.

## Конфигурация

```json
{
  "rag": {
    "enabled": true,
    "strategy": "structured",
    "candidateTopK": 20,
    "topK": 4,
    "queryRewrite": true,
    "rerank": { "enabled": true, "minRelevance": 2 },
    "indexRunId": "ID существующего запуска индексации"
  }
}
```

`candidateTopK` — целое число от `topK` до 30; `topK` — максимум 1–8 фрагментов для ответа. Порог `minRelevance` — 0–3. Необязательный `minSimilarity` (−1…1) отсекает кандидатов по cosine ещё до реранкера. По умолчанию cosine-фильтр выключен: универсального порога для всех моделей и вопросов нет. Без `indexRunId` используется последний индекс. Без новых параметров старый RAG сохраняет прежнюю схему поиска.

Общая страница «RAG» сравнивает четыре обычных агента: без RAG, structured, fixed и улучшенный structured с rewrite + реранкингом. У них одинаковые модель `deepseek-v4-flash`, `temperature: 0` и системный промпт. Все RAG-агенты закреплены за одним запуском индекса. Настройки улучшенного режима заданы в конфигурации агента, на экране нет отдельного редактора параметров.

Для подробных экспериментов CLI сохраняет четыре режима Day 23:

| Режим | Rewrite | Реранкинг / фильтр | Финальный контекст |
| --- | --- | --- | --- |
| Базовый RAG | Нет | Нет | Первые 4 из 20 cosine-кандидатов |
| Реранкинг и фильтр | Нет | Да | До 4 прошедших порог |
| Только query rewrite | Да | Нет | Первые 4 после объединения двух поисков |
| Rewrite + реранкинг | Да | Да | До 4 прошедших порог после объединения |

В общей демонстрации cosine-фильтр выключен. Для отдельного агента его можно включить в конфигурации.

## Путь запроса

1. Rewrite той же LLM превращает исходный вопрос в поисковую формулировку. Он не видит ожидаемые ответы или документы. Идентификаторы, отрицания и смысл требуется сохранить. Ошибка rewrite явно отображается, поиск продолжается по исходному вопросу.
2. Ollama строит эмбеддинги исходного и переписанного вопросов одной пачкой, моделью и профилем выбранного индекса.
3. SQLite ищет до 20 кандидатов для каждого запроса. При rewrite выдачи объединяются по reciprocal rank fusion (`1 / (60 + rank)`), дубликаты удаляются по `chunkId`; общий пул ограничен 20. Поиск по исходному вопросу не заменяется переписанным, но RRF может изменить порядок и состав итогового пула.
4. Необязательный cosine-порог удаляет слабые кандидаты.
5. Listwise-вызов LLM получает исходный вопрос и весь оставшийся пул. Для каждого ID он возвращает оценку и краткое обоснование, а также порядок полезности. Оценки: **0** — нерелевантно; **1** — общая тема без ответа; **2** — часть необходимых фактов; **3** — прямой ответ или существенная его часть. Это категории, не вероятности. Если модель пропустила ID, выполняется один дополнительный вызов только для недостающих чанков; корректные оценки первого вызова сохраняются. При невалидном JSON, неизвестных/повторных ID или неверных оценках весь некорректный пакет запрашивается повторно, без доверия к его содержимому.
6. Сохраняются оценки ≥2, выбираются максимум 4 лучших. Если прошли два — передаются два, если ни одного — пустой контекст. Нерелевантными фрагментами контекст не дополняется.
7. Стандартный агент отвечает на исходный вопрос, получив только отобранные источники. Без источников сообщает, что подтверждения в проекте нет; общие знания должен помечать отдельно. В историю сохраняются вопрос и ответ, а не копия корпуса.

Текст каждого кандидата ограничен 3600 символами **до** реранкинга. Реранкер, генератор и UI видят один и тот же текст. Ответ реранкера проверяется: все переданные ID ровно один раз, целая оценка 0–3, непустое обоснование. Если после двух попыток остаются неоценённые чанки, запрос завершается явной ошибкой с количеством полученных/ожидаемых оценок, а не скрытым переходом к baseline. `rag.trace.rerank.attempts` и `warning` сохраняют диагностику повтора. Сбой Ollama, неизвестный индекс и отсутствие стратегии тоже дают ошибку.

Rewrite имеет таймаут 45 секунд, каждый вызов реранкера — 90. Если внутренний `Agent.run` выполняется с `AbortSignal`, отмена передаётся также rewrite, embedding и реранкеру. Закрытие браузерного `/stream` само по себе не отменяет вспомогательные вызовы: остаются их таймауты. Лимиты генерации для них отдельные: 400 и 4096 токенов. Точные `promptTokens`, `completionTokens`, `totalTokens` включают вспомогательные вызовы, включая повторную оценку; `rag.trace.usage` отдельно показывает их стоимость в токенах. Неуспешный запрос не сохраняет успешный ответ; расход провайдера при ошибке может не быть отражён в отчёте.

## Демонстрация в React

1. Откройте приложение `http://127.0.0.1:5173` → **RAG**. Отдельная сложная страница Day 23 удалена.
2. Нажмите **Создать или обновить агентов**, если кнопка доступна. Обновление конфигураций не удаляет историю или ответы на странице.
3. Нажмите **Получить ответы на все 10 вопросов**. Для каждого вопроса рядом показываются четыре ответа; ожидание и ожидаемые источники находятся над ними. Можно раскрывать найденные источники.
4. Результаты автоматически сохраняются в IndexedDB браузера после каждого вопроса. Их можно скачать как JSON или очистить для следующего теста. Хранилища Safari и других браузеров независимы; удаление данных сайта удаляет браузерные результаты.
5. При переходе со старого экрана сохранённые baseline/full ответы из наиболее полного совместимого прогона переносятся в structured/улучшенный RAG без повторных API-вызовов. Без RAG и fixed не подменяются другими ответами: при отсутствии сохранённых данных остаются пустыми до нового запуска. Исходные отчёты Day 23 сохраняются в браузере.
6. **Очистить тесты агентов** после подтверждения удаляет историю трёх агентов Day 22 и `day23-full`, а также очищает текущее сравнение. Конфигурации, индекс и прежние отчёты Day 23 остаются. Новый тест использует отдельный `conversationId` для каждого вопроса, так что предыдущие вопросы не влияют на ответы.

Изолированные режимы, дополнительные четыре вопроса и подробная диагностика доступны через CLI. Это позволяет проводить эксперимент, не усложняя основной экран сравнения.

Обрабатываются реальные ответы API, не фиксированный текст. Ожидания и источники для оценки заданы в `src/rag-questions.ts` и `src/rag-day23-questions.ts`; в промпты rewrite, реранкера и ответа они не передаются. Эти файлы, документы с оценками и тестовые fixtures исключены из **новых** индексов. Для честного сравнения текущий индекс не пересобирался между режимами.

В DeepSeek уходят вопросы и найденные фрагменты проекта. Ключи и `.env` в корпус не входят. Baseline требует один вызов LLM, rewrite-only/rerank-only обычно — до двух, полный режим обычно — до трёх. При исправлении невалидного результата реранкера добавляется один вызов. Пустой кандидатный пул пропускает реранкинг. Повторные прогоны платные.

## CLI и контрольные результаты

```bash
# Baseline и full, 10 вопросов, с реальными ответами
npm run rag:evaluate -- --answers
# 14 вопросов, включая перефразирования и вопросы вне базы
npm run rag:evaluate -- --extended --modes baseline,full --answers
# Изолировать эффект каждого этапа на вопросе №9
npm run rag:evaluate -- --question-id 9 --modes baseline,rerank,rewrite,full --answers
# Только оценка поиска: генерация финального ответа выключена
npm run rag:evaluate -- --modes baseline,full
```

CLI закрепляет индекс на старте и сохраняет JSON в `data/rag-day23/<uuid>.json` (не коммитится). Можно указать `--strategy`, `--candidate-top-k`, `--top-k`, `--min-relevance`, `--min-similarity`, `--index-id`, `--output`. Вывод только поиска не импортируется как отчёт с ответами.

Контрольный прогон 03.10.2026: индекс `d7864665-db3b-43cf-9c71-bb2e30365369`, `structured`, `nomic-embed-text-v2-moe`, 20 → 4, relevance ≥2, без cosine-фильтра. Один фиксированный корпус для обоих режимов, модель `deepseek-v4-flash`. Отчёт: `data/rag-day23/1b424b2f-eb9d-4741-b863-fede94c2125c.json`.

| Метрика | Baseline | Rewrite + реранкинг |
| --- | ---: | ---: |
| Все контрольные фрагменты в контексте, исходные 10 вопросов | 9/10 | 10/10 |
| С учётом двух перефразирований | 11/12 | 12/12 |
| Все фрагменты среди 20 кандидатов | 12/12 | 12/12 |
| Пустой контекст на двух вопросах вне базы | 0/2 | 2/2 |
| Ответы без ошибок API | 14/14 | 14/14 |
| Суммарные токены всех 14 запросов | 23 821 | 156 669 |
| Среднее время запроса | 1,71 с | 6,87 с |

На вопросе №9 нужный контрольный фрагмент был ниже top-4. Изолированный прогон всех четырёх режимов включил его только с реранкингом; rewrite-only его не поднял. Значит на этом вопросе полезен именно второй этап.

**Качество ответов не равно покрытию фрагментов.** Ручная проверка минимальных ожидаемых фактов исходных 10 вопросов: оба режима передали их в 10/10 ответах. Baseline смог ответить на №9 по другим фрагментам кода, несмотря на отсутствие конкретной контрольной цитаты. Нельзя заявлять рост точности ответов с 90% до 100% по этой метрике поиска. На внешних вопросах оба режима корректно отделили отсутствие проектных данных от общих знаний; улучшенный режим не отправлял генератору случайные CSS-фрагменты.

Найдены ограничения: зафиксированный индекс содержит снимок **до Day 23**. Ответ №9 в full пересказывает старую реализацию (latestRun и ошибка при пустой выдаче), а не новые этапы; это проблема актуальности корпуса, не отсутствие реранкинга. Полезность по минимальному ожиданию не означает безошибочность всех дополнительных утверждений модели. После завершения сравнительного эксперимента индекс следует обновить для вопросов о текущем коде.

Порог 2 и top-K 4 выбраны как стартовый компромисс. Повторное применение порогов 1/2/3 и top-K 2/4/6 к сохранённым оценкам этого прогона оставило покрытие 12/12 и пустой контекст 2/2 одинаковыми. Это **офлайн-проверка отбора**, не новые генерации ответов и не доказательство оптимальности настроек. Для реальной калибровки нужен более разнообразный набор. Реранкер не вернёт факт, отсутствующий среди кандидатов, и не исправит плохой/устаревший документ.

## Автоматические проверки

```bash
npm run test:rag
npm run test:rag:agent
npm run test:rag:retrieval
npm run typecheck
npm run build
```

Проверяются обратная совместимость, закреплённый индекс, rewrite с fallback, объединение/дедупликация, подъём седьмого кандидата, пороги без дополнения мусором, пустой контекст, невалидный JSON, одинаковое ограничение текстов, отмена и учёт токенов для run/stream, импорт отчётов и независимость оценки ответа от покрытия цитат.
