# Независимая оценка ответов DeepSeek

Агент проверки использует `deepseek-v4-pro`, thinking=enabled, reasoning_effort=high. Модель подтверждена списком `/models` настроенного аккаунта. [Документация моделей](https://api-docs.deepseek.com/api/list-models/), [режим рассуждений](https://api-docs.deepseek.com/guides/thinking_mode/).

На один вопрос агент получает полные материалы с id и два ответа A/B. Порядок A/B меняется между вопросами. Названия локальных профилей, параметры, время, эталоны и результаты текстовых проверок ему не передаются. Это отдельный облачный запрос после генерации локальных ответов, без инструментов и доступа к проекту.

Агент сравнивает смысл утверждений с материалами: числа, отрицания, условия, причинные связи, полноту всех подпунктов, область действия и различие подсистем. Для каждой стороны он возвращает:

- точность, полноту и опору на материалы — отдельно по 0–5;
- правильность привязки ссылок к утверждениям — отдельно по 0–5;
- вердикт correct/partial/incorrect;
- краткое обоснование, конкретные ошибки и пропуски.

Итог /10 вычисляется из точности (50%), полноты (30%) и опоры на материалы (20%). Ссылки показаны отдельно, чтобы отсутствие ссылок у исходного общего помощника не превращалось автоматически в фактическую ошибку. При отсутствии данных оценивается честность отказа, а не совпадение точной фразы.

Первичная проверка регулярными выражениями остаётся технической диагностикой в JSON и историческом подборе параметров. На странице качество показывает только реальную оценку агента DeepSeek. До её получения стоит прочерк. Ошибка API не заменяется текстовым баллом. Агентная оценка тоже может ошибаться; её обоснование и найденные нарушения доступны рядом с ответом.

Оценки, модель, дата, рубрика, хэш вопроса/материалов/ответа, длительность и токены сохраняются в отчёте. Изменение ответа, материалов, prompt проверяющего или модели делает старую оценку неактуальной. Время, скорость и память локальной LLM не включают работу облачного проверяющего. Длительность и токены DeepSeek относятся к одному запросу на пару и повторяются в метаданных обеих оценок; их нельзя суммировать как два запроса.

На странице есть «Проверить ответы DeepSeek» и проверка отдельного вопроса. Новый запуск вопроса автоматически оценивает полученную пару, если ключ настроен. При запуске всех вопросов локальная генерация последовательна, а до трёх готовых пар оцениваются в DeepSeek одновременно, в том числе во время получения следующих локальных ответов. Отдельная проверка использует сохранённые ответы и не запускает локальную модель заново. Ключ остаётся на сервере. В DeepSeek передаются вопрос, фрагменты документации и оба ответа — подготовленный набор доступен в [day-29-judge-inputs.json](day-29-judge-inputs.json).

```bash
npm run llm:optimize:review
npm run llm:optimize:review -- --case=memory
```

CLI пропускает актуальные сохранённые оценки; `--force` запускает их повторно. Настройка модели — `DEEPSEEK_JUDGE_MODEL` в `.env`, число параллельных проверок — `DEEPSEEK_JUDGE_CONCURRENCY` (по умолчанию 3, допустимо 1–5). Это ограничение применяется к пакетам UI и CLI. API: `POST /api/llm-optimization/review` для всех пар, с `{caseId}` для одной или `{caseIds: [...]}` для выбранного пакета; `/compare` также принимает одну или несколько caseIds. Ответ — NDJSON с отчётами и прогрессом: текущий локальный вопрос, активные проверки DeepSeek и число завершённых. Остановка отменяет все активные запросы, прекращает запуск оставшихся и сохраняет завершённые оценки.

Параллельные результаты объединяются по конкретному вопросу, а запись отчёта выполняется последовательно. Поздний ответ не перезаписывает уже полученные оценки других вопросов или новые локальные ответы. Вызовы Ollama не выполняются одновременно, чтобы не смешивать замеры скорости и памяти. Модель, режим high и содержательная рубрика оценщика сохранены. Ускоряется обработка пакета; время одного запроса зависит от DeepSeek. [Официальные лимиты параллельных запросов](https://api-docs.deepseek.com/quick_start/rate_limit/).

Если финальный ответ DeepSeek пустой или нарушает JSON/схему полей, сервер делает один дополнительный запрос по той же рубрике и с теми же анонимными ответами, уточняя ошибку формата. Полный корректный пример задан для A и B. Один JSON-блок в Markdown допускается; дробные баллы, строки вместо чисел, пропущенные и лишние поля по-прежнему отклоняются. Приложение не округляет и не додумывает оценки. Ошибки HTTP, незавершённые ответы и отмена пользователем не запускают этот повтор.

При нарушении формата финальный текст и причина сохраняются локально в `data/day-29-judge-diagnostics/`; ключ API и ход рассуждений туда не попадают. Если повтор тоже неудачен, UI называет проблемное поле. Содержательная рубрика не меняется при уточнении формата, поэтому прежние действительные оценки сохраняются. Длительность и токены проверки учитывают обе попытки, если понадобился повтор; локальные ответы и их метрики не меняются.

Новый `llm:optimize:tune` также выбирает параметры по оценкам DeepSeek вместо текстовых совпадений. Он получает три фиксированных исходных ответа, оценивает каждый вариант вслепую относительно них и проверяет адаптивный контекст. Новый отчёт — `docs/day-29-tuning-agent.json`; прежний числовой подбор сохраняется отдельно. Этот новый подбор в рамках добавления проверяющего не запускался: текущие параметры не изменялись, оцениваются уже сохранённые ответы. Для будущего подбора необходим ключ DeepSeek; отказ проверяющего останавливает выбор параметров без подстановки regex-баллов.

39 тестов проверили анонимизацию, отсутствие эталонов/настроек в запросе, сопоставление A/B, формат и диапазон оценок, автоматический повтор при ошибке формата, диагностику, ошибки API, отмену, ключи, актуальность оценок, выбор параметров по семантической оценке и сохранность локальных метрик. Для параллельных прогонов отдельно проверены ограничение числа запросов, последовательная генерация и запись файлов, завершение в разном порядке без потери результатов, отмена и защита от устаревшей оценки. TypeScript и production-сборка прошли.

## Реальный прогон — 12 октября 2026

После согласия пользователя DeepSeek Pro оценил все 10 пар — 20 сохранённых ответов. Полные оценки, обоснования, ошибки, пропуски и метаданные: [day-29-judge-results.json](day-29-judge-results.json). Модель, возвращённая API во всех оценках: deepseek-v4-pro. Один запрос превысил прежний таймаут; повтор только этой пары с увеличенным ожиданием завершился успешно. Сохранённых ошибок проверки нет. На один облачный запрос приходятся две оценки; всего 10 успешных запросов и одна попытка с таймаутом.

| Показатель агента | До | После |
| --- | ---: | ---: |
| Средний итог /10 | 8.74 | 10.00 |
| Точность /5 | 4.30 | 5.00 |
| Полнота /5 | 4.60 | 5.00 |
| Опора на материалы /5 | 4.20 | 5.00 |
| Ссылки /5 | 0.70 | 5.00 |

Примеры: одинаково правильные простые ответы получили по 10/10; ошибочное удаление Working в исходном ответе — 7.2/10 против 10/10 после; неверное утверждение об отсутствии значений в длинном регламенте — 4.6/10 против 10/10. Проверяющий также нашёл смешение кнопок «Новый диалог» и «Очистить чат» в исходном составном ответе — 6.2/10 против 10/10. Баллы — суждение одного агента по зафиксированной рубрике, не процент доказанной фактической точности.

## Ошибка формата при последующем запуске — 12 октября 2026

В пользовательском повторном прогоне вопрос `scheduler-recovery` получил ошибку разбора JSON/полей. Старый обработчик не сохранял финальный ответ при такой ошибке, поэтому конкретное нарушение исходной попытки восстановить нельзя. Отдельный диагностический повтор завершился HTTP 200, `finish_reason=stop` и корректной схемой: постоянная ошибка API не воспроизвелась. В старом prompt был неполный пример объекта B (`те же поля`) и отсутствовал повтор при ошибке формата.

Добавлены полный пример для обеих сторон, строгая проверка без подстановки баллов, один повтор и диагностика. Проверка только вопроса 7 через кнопку в UI завершилась успешно: 10/10 до и 9.4/10 после по суждению агента. В актуальном пользовательском отчёте оценены все 20 ответов, ошибок проверки нет; хэши всех локальных ответов вместе с метриками и остальных девяти пар оценок совпали до/после повторной проверки. Исторический отчёт первого прогона выше не перезаписан.

## Проверка параллельной оценки — 12 октября 2026

Через обновлённый `/review` одновременно отправлены три сохранённые пары: `storage`, `missed`, `memory`. Максимум активных проверок — 3; все шесть оценок вернулись от `deepseek-v4-pro` без ошибок. Пакет занял 61.10 секунды. Прогресс и метаданные сохранены локально в `data/day-29-parallel-review-check.json`. Это проверка конкретных трёх пар, а не замер ускорения всех десяти сложных вопросов относительно отдельного последовательного прогона.

Хэши всех локальных ответов вместе с метриками и оценок оставшихся семи пар совпали до/после. Все 20 текущих оценок остаются действительными. Браузерная страница обновлена; показывает лимит трёх одновременных проверок.
