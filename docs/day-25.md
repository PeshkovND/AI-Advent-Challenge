# День 25 — мини-чат с RAG и памятью задачи

На отдельной странице **RAG-чат** — диалог в стиле ChatGPT: сообщения пользователя справа, ответы ассистента в ленте, поле ввода снизу, сохранённые диалоги слева. Источники и дословные цитаты находятся под документальными ответами и ответами по памяти; для обычного общения и общих знаний явно показывается «Без поиска по документам». Компактная панель «Память задачи» показывает цель, уточнения, ограничения и термины с номером исходного сообщения пользователя.

## Запуск и демонстрация

```bash
npm run dev
```

Откройте `http://127.0.0.1:5173`, раздел **RAG-чат**. Нужны работающие Ollama, существующий локальный индекс и серверный ключ DeepSeek. При первом открытии создаётся обычный агент `day25-rag-chat` через `POST /api/agents`. Он закрепляет текущий индекс; обновление страницы не пересоздаёт агента и не меняет индекс старых диалогов.

1. Начните с карточки «План демонстрации RAG»: она подставляет текст в поле, но не отправляет платный запрос автоматически.
2. Зафиксируйте цель, ограничения и значение термина; задавайте вопросы по документам и уточнения вроде «а как в нём ищут?».
3. Через несколько сообщений попросите напомнить исходную цель. Откройте «Память задачи» и «Источники и цитаты».
4. Измените одно ограничение явно: «новые библиотеки теперь разрешены, но внешние базы по-прежнему запрещены». Проверьте актуальную память.
5. Обновите страницу: история, память и цитаты восстановятся с сервера.
6. «Новый чат» создаёт отдельный `conversationId`, не стирая старый диалог. В новом чате старая цель не используется.
7. Значок корзины рядом с диалогом удаляет его после подтверждения: историю, цитаты, память задачи и счётчики токенов. Другие диалоги и конфигурация агента сохраняются. При удалении открытого диалога начинается пустой новый чат; на узком экране корзина текущего диалога находится в заголовке. Восстановления удалённых диалогов нет.

Ответ с фактами о проекте опирается на документы индекса. Напоминание пожеланий/цели опирается на цитаты сообщений пользователя, помеченные **«Слова пользователя, не документация проекта»**. Это разные классы источников; слова пользователя не подтверждают реализацию проекта. Если подтверждения нет, ответ — «Не знаю» с уточнением, блок источников явно сообщает об отсутствии подтверждения. Выдуманных цитат для такого ответа нет.

## Конфигурация обычного агента

```json
{
  "provider": "deepseek",
  "model": "deepseek-v4-flash",
  "temperature": 0,
  "dialogueMemory": { "enabled": true, "historyWindow": 6 },
  "rag": {
    "enabled": true,
    "strategy": "structured",
    "retrievalPolicy": "auto",
    "candidateTopK": 20,
    "topK": 4,
    "queryRewrite": false,
    "rerank": { "enabled": true, "minRelevance": 2 },
    "grounding": { "enabled": true },
    "indexRunId": "ID существующего индекса"
  },
  "inputPolicy": { "maxCharacters": 8000 }
}
```

`dialogueMemory` — **память задачи диалога**, не Day 13 `taskMachine` с этапами planning/execution/validation. Режим опциональный: остальные агенты и страница сравнения Day 22–24 не меняются. Для него обязательны RAG и grounding; смешивание с `taskState`, MCP-действиями, другими стратегиями контекста и включёнными `memoryLayers` отклоняется. Окно истории — чётное число от 2 до 20 сообщений, по умолчанию 6 (3 пары); полная история сохраняется независимо от окна.

Здесь contextual rewrite выполняет этап памяти, поэтому дополнительный обычный `rag.queryRewrite` выключен: это не отказ от переписывания вопроса, а отсутствие дублирующего LLM-вызова. Настройки поиска/фильтрации по-прежнему принадлежат `rag` в конфигурации агента.

## Путь каждого сообщения

1. Обычный `POST /api/agents/day25-rag-chat/run` получает `{input, conversationId}`. Клиент не отправляет историю или состояние памяти: они читаются из серверного хранилища своего диалога.
2. Отдельный JSON-вызов модели получает предыдущую память, три последних сообщения **пользователя**, короткое окно диалога и текущий input. Он предлагает точечные изменения памяти и самостоятельную формулировку текущего вопроса. Ответы ассистента помогают разрешать ссылки, но не становятся фактами памяти или доказательствами реализации.
3. Сервер проверяет транспортный JSON и дословное происхождение цитат, затем применяет точечные изменения к копии памяти. Не упомянутые записи сохраняются. Замена/отмена существующей записи требует `previousQuote` прежней записи; отдельный смысловой аудит проверяет, действительно ли пользователь разрешил это изменение. Произвольные пожелания хранятся текстом, без перечня допустимых видов настроек. Есть технические бюджеты объёма (256 записей на группу и 100 000 символов снимка), но нет прежнего ограничения на 12 пожеланий и нет тихого вытеснения. Невалидное извлечение исправляется один раз; затем сохраняются прежняя память, исходное сообщение и ссылка `pendingTurns` для последующего восстановления, а пользователю задаётся уточнение.
4. При `rag.retrievalPolicy: "auto"` тот же JSON-вызов подготовки памяти выбирает режим и краткую причину: `documents` — вопрос о проекте/продолжение такого вопроса; `dialogue` — вопрос о ранее сохранённых целях/пожеланиях; `preferences` — принятие, изменение или отмена настройки без информационного вопроса; `conversation` — приветствие/благодарность; `general` — явно общий вопрос; `clarification` — неоднозначная просьба или конфликт требований. Только `documents` запускает поиск: эмбеддинг самостоятельного вопроса в Ollama → cosine top-20 → LLM-реранкинг по вопросу → отсечение оценок ниже 2/3 → максимум 4 чанка. Дополнительного router-вызова нет. При сомнениях выбран поиск; «привет» вместе с вопросом о проекте тоже требует документов. Наличие старой цели не превращает простое приветствие в поиск. Контрольные ожидания сценариев в эти вызовы не передаются.
5. Модель ответа получает последние 6 сообщений (без повторной передачи старых блоков цитат), компактную память, исходный вопрос, раскрытую формулировку и свежие документы. Предыдущие ответы не являются доказательством новых фактов.
6. Для документального вопроса пустой контекст даёт «Не знаю», а не догадку из общих знаний. Если есть пожелания пользователя, отдельная генерация и проверка оформляют отказ на нужном языке и в нужном формате, без добавления фактов или цитат. Напоминание цели подтверждается цитатами пользователя без поиска документов. Принятие настройки — короткое подтверждение, без фактической проверки и без «не знаю». Приветствия и явно общие вопросы идут через обычный LLM completion с историей и памятью, без эмбеддингов, реранкинга и обязательных цитат. Если есть пожелания, проверяется их соблюдение. Модель не должна выдавать общее знание за проверенные сведения о проекте. Классификация намерения — модельная и может ошибаться, не специальный обработчик контрольных вопросов. Память сохраняется во всех режимах.
7. Сохраняются проверки Day 24: строгий JSON утверждений, настоящие ID, непрерывные дословные цитаты и отдельная LLM-проверка смысловой поддержки. Проверяющий также различает документы/слова пользователя и оценивает **весь ответ**: сохранена ли цель, выполнена ли текущая просьба, соблюдены ли актуальные ограничения. При пожеланиях отдельно проверяется видимый Markdown без длинных блоков доказательств: внутренний JSON-массив утверждений не считается списком ответа. Результат — `verification.taskCheck`. При нарушении разрешена одна полная регенерация с повторной проверкой. Если факты подтверждены, но оформление всё ещё не совместилось, выдаётся проверенный уточняющий вопрос, а не «не знаю» или ошибка типа настройки. Ошибки сети и непроверяемые доказательства не маскируются успешным ответом.
8. После полного проверенного ответа или уточнения одним сохранением истории фиксируются новая пара сообщений, снимок памяти, цитаты и поисковый вопрос. Сбой провайдера/поиска не продвигает память и не сохраняет частичный ход. Неразобранное извлечение сохраняет исходный текст после проверенного уточнения; следующие ходы могут восстановить его по настоящей цитате и номеру пользователя, не откатывая более новые правила. Корректный отказ «Не знаю» тоже сохраняет однозначные изменения памяти.

Обычный `/stream` тоже поддерживается: строгий ответ буферизуется до проверки, сохраняется один раз, затем отдаётся целиком. На странице используется `/run`, чтобы не показывать неподтверждённые промежуточные токены. Одновременный второй запрос в один диалог возвращает 409; разные диалоги изолированы.

## Хранение и API

Полная история, снимки памяти и проверенные цитаты — в `data/agent-state.json`, исключённом из Git. Ключ хранения — `agentId::conversation::conversationId`. Запись использует существующую очередь и временный файл с атомарным rename. После перезапуска последний сохранённый снимок памяти берётся из последнего ответа своего диалога.

Добавлены возможности обычного агентного API, без отдельного сервиса генерации:

- `GET /api/agents/:id/conversations` — список сохранённых диалогов;
- `GET /api/agents/:id/history?conversationId=...` — история с цитатами, память и токены конкретного диалога;
- `DELETE /api/agents/:id/history?conversationId=...` — очистка только указанного диалога;
- `POST /api/agents/:id/run` и `/stream` — прежние методы, с обычным `conversationId`.

В ответе `/run` дополнительно `dialogueMemory`, `resolvedQuestion` и `retrieval: {policy, route, searched, reason}`; найденные документы — `rag.sources`, использованные доказательства и цитаты — `rag.grounding`. Для ответа только по памяти нет `rag`, подтверждения находятся в верхнеуровневом `grounding`. Цитаты диалога имеют `kind: "dialogue"`. Решение о поиске сохраняется в истории; `searchQuery` сохраняется только при фактическом поиске. Токены этапов памяти и всех проверок входят в общие метрики один раз. Обычно 4 вызова DeepSeek для документов без пожеланий, 5 с отдельной проверкой оформления, 3 для цитируемой памяти (4 с пожеланиями), 3 для настройки/уточнения или обычного ответа с пожеланиями и 2 для обычного общения/общих знаний без пожеланий. Замены/отмены добавляют аудит памяти; исправления добавляют вызовы. Ollama вызывается только при поиске.

## Пожелания и формат ответа

«Отвечай нумерованным списком» сохраняет настройку и получает подтверждение в таком же формате, а не ответ об отсутствии доказательств. Если настройка сопровождается вопросом, она сохраняется и применяется к ответу в соответствующем режиме.

Каждое независимое пожелание — запись `{key, text, quote, userTurn}` с произвольным стабильным ключом и текстом естественным языком. Нет enum видов пожеланий, `preferenceBindings`, перечня форматов или запрещённых семантических ключей. Например, «сначала метафора», «не употребляй это слово», «объясняй для новичка», «суть, затем таблица» — обычные записи. Четыре группы лишь организуют цель/уточнения/ограничения/термины; неизвестная текстовая категория помещается в ограничения. Старые аннотации типов игнорируются при чтении, сами пожелания и их происхождение сохраняются.

Добавление лимита пунктов не стирает краткость, язык или аудиторию. Замены и отмены — отдельные операции с точной ссылкой на прежнюю цитату и проверкой смысла. Повтор неизменённого правила идемпотентен. Неоднозначную отмену и противоречивые требования агент должен уточнить, не выбирая молча. Разовые указания передаются только текущей генерации и не записываются в постоянные пожелания. Приоритет: безопасность и достоверность → текущее разовое указание → актуальное постоянное правило → настройки по умолчанию. Независимые правила сосуществуют.

Сервер сохраняет предложенный моделью Markdown, добавляя только проверенные ссылки. Проверка пожеланий модельная, а не жёсткое форматирование по нескольким типам. Два неудачных разбора памяти приводят к уточнению с сохранением исходного сообщения для восстановления. Неуспешное оформление исправляется, затем при необходимости уточняется; оно не считается отсутствием доказательств. Происхождение памяти, цитат и атомарность сохранения проверяются кодом.

Необработанные старые сообщения не откатывают более новые записи. Пока они есть, отмены оставляют технические ревизии `removed`, чтобы восстановление старого сообщения не воскресило отменённое правило. После разбора этих сообщений метки очищаются. `replyInstructions` в ответе `/run` показывает только текущие разовые указания для диагностики; это не постоянная настройка, и в следующем ходе она не берётся из прошлого ответа.

Ограничения длины относятся к основному ответу: источники и дословные цитаты не обрезаются. Пользовательские пожелания не отменяют проверку фактов и правила безопасности. Абсолютной гарантии понимания любых формулировок нет: извлечение и часть проверки остаются модельными.

### Проверка свободной памяти 5 октября

Через обычный API выполнены два сценария по пять разных сообщений: нестандартный составной формат, аудитория новичка и запрещённое слово; разовый список; замена постоянного оформления; напоминание цели; явный конфликт; английский язык, метафора и запрет эмодзи; разовый русский ответ; отмена только метафоры; документальный поиск и напоминание памяти после перезапуска. Всего 14 платных пользовательских сообщений: первоначальные 12 и два отдельно разрешённых заключительных. Отчёт: `data/rag-day25/preferences-ace2d045-1ff4-46f7-8db8-fec81f5ce3b7.json`, 231 042 токена с вспомогательными этапами.

В первом прогоне ответ абзацами был ошибочно принят фактическим verifier за маркированный список. Добавлены проверка видимого Markdown без длинных цитат и явное указание генератору, что массив `claims` не является списком в UI. Четыре неудачные попытки сохранены в отчёте; после исправлений разовый список, замена на два абзаца, избирательная отмена, смена языка и конфликт прошли проверки. Первый ответ с таблицей повторял вступительную суть: автоматический тест этого не заметил, поэтому результаты не называются гарантией качества «10/10» и этот ответ не выдаётся за повторный прогон последней версии. Новый проверяющий отдельно запрещает такое дублирование.

Перед заключительными вопросами React, API и Ollama перезапущены. Отпечатки обеих тестовых историй до/после совпали полностью; восстановились цель, пожелания и цитаты. Заключительные документальный ответ и напоминание памяти получены на английском, без отменённой метафоры и эмодзи. Первоначальная языковая проверка дала ложное срабатывание на дословный русский аргумент внутри CLI-примера; она исправлена на проверку прозы вне кода, старый ответ перепроверен локально без повторного запроса и без изменения текста модели.

Повтор реального прогона требует отдельного разрешения на платные вызовы:

```bash
node --import tsx server/rag-chat-preferences-evaluate.ts --flexible
```

При остановке `--resume data/rag-day25/preferences-<uuid>.json` сохраняет исходный общий предел 12 сообщений, включая повторы. `--extra-two-approved` поднимает его до 14 только для этого же flexible-отчёта и используется исключительно после отдельного разрешения двух дополнительных сообщений.

### Исторические проверки прежней версии 5 октября

Ниже результаты прежнего ограниченного контракта, не доказательство качества новой свободной памяти. Пределы числовых типов и исправление `preferenceBindings` относятся только к той версии.

Выполнено 20 согласованных сообщений через обычный `/run`, в отдельных тестовых диалогах. Проверены приветствие, настройки без вопроса, смешанный вопрос с целью и ограничениями, нумерация, разовый формат, отмена лимита, смена языка, краткие ответы по документам, напоминание памяти и отказ на вопрос вне базы. 19 запросов вернули ответ с сохранённой историей; один запрос остановился на строковом числовом лимите `"40"`. После безопасной нормализации десятичных строк этот шаг повторён успешно. Числа из произвольных слов и boolean не принимаются.

Отчёт: `data/rag-day25/preferences-40405a54-2439-4628-869c-d6c1695bb4d8.json`. Автоматические проверки первоначальных двух сценариев не заметили потерю «кратко» при добавлении лимита одного пункта: ручная проверка нашла замену под общим ключом `answer_length`. После этого настройки разделены и добавлены локальные проверки независимости, отмены одного правила, восстановления после перезапуска и отсутствия частичных изменений при ошибке ответа. Последний, 20-й запрос проверил сохранение трёх отдельных настроек в новом диалоге. Два дальнейших шага проверки их сохранения при новом лимите остановлены по согласованному бюджету; прежние результаты не считаются повторным прогоном исправления.

Позднее исправлена ошибка `preferenceBindings[0].name`: схема ответа принимала пять типов, тогда как память поддерживала также `verbosity` и `tone`. Последний вопрос пользователя содержал «Отвечай кратко»; сырой невалидный ответ модели не сохранён, поэтому конкретное недопустимое имя в первоначальном вызове не установлено. После согласования схем выполнены два отдельно разрешённых сообщения через DeepSeek в новом тестовом диалоге: исходный вопрос о двух стратегиях с целью, запретами и краткостью; затем «А чем эти две стратегии отличаются?». Оба завершились без ошибки, с дословными цитатами, проверенными утверждениями и сохранённой памятью. Исходный ответ назвал `fixed` и `structured`; продолжение привело больше подробностей, чем минимальное сравнение — это не абсолютная гарантия краткости. Отчёт: `data/rag-day25/preferences-a63a0217-b8c7-4802-9f1a-9573c1da5d5b.json`, 38 016 токенов. Повтор такого короткого прогона (два платных сообщения, требуется разрешение): `node --import tsx server/rag-chat-preferences-evaluate.ts --probe-brevity`.

Если `retrievalPolicy` не указан или равен `"always"`, сохранено прежнее поведение: поиск на каждом сообщении. Поэтому остальные агенты Day 22–24 не меняются. `auto` требует включённой `dialogueMemory` и проверяемых цитат; выбор режима доступен через обычную конфигурацию агента, без отдельного API или кнопок. Обновление UI само не меняет существующую конфигурацию. Старые ответы, включая ошибочный отказ на приветствие, не переписываются.

Для доказательств памяти отправляются её дословные фрагменты из оригинальных сообщений, а не все полные сообщения пользователей. Это не пересказ и не склейка несмежных фрагментов в одну цитату. Длинные исходные сообщения остаются в истории. Транспортный бюджет цитаты памяти — 8000 символов; в конкретном ответе доказательство — непрерывный фрагмент до 1200 символов.

## Два длинных сценария

Набор в `src/rag-chat-scenarios.ts`: **2 сценария по 12 сообщений пользователя** (24 сообщения с ответами в каждом диалоге).

- Демонстрация локального RAG: цель пятиминутного выступления, structured vs fixed, пользовательское определение «контекст», вопрос с местоимением, изменение запрета библиотек, итог по исходной цели.
- Чек-лист фоновых задач: хранение/захват worker, пропущенные запуски, Asia/Omsk, определение «сводка», read-only календарь, разрешение новых зависимостей и финальное напоминание цели.

```bash
# Платные реальные вызовы обычного API агента
npm run rag:check-chat
# Только один сценарий
npm run rag:check-chat -- --scenario rag-demo
npm run rag:check-chat -- --scenario scheduler-review
```

Проверка создаёт отдельный conversationId для каждого сценария, не очищает пользовательские чаты и результаты Day 24. В JSON `data/rag-day25/<uuid>.json` после каждого сообщения сохраняются ответ, актуальная память, ожидание, ожидаемые источники и отдельные проверки: сохранение истории, соответствие поиска типу вопроса (в `auto` напоминания памяти не требуют поиска), удержание цели, происхождение памяти, актуальность уточнений/отмен, наличие/класс источников, дословность цитат и результат смысловой проверки. Сценарии и документация задания исключены из индексируемого корпуса, чтобы ожидания не попали в контекст.

Дословность и происхождение цитат проверяются кодом. Смысл, разрешение ссылок и извлечение памяти проверяются LLM и вручную: прохождение контрактов не означает гарантированную полноту/качество ответа. Индекс остаётся снимком проекта до Day 23; ответ может корректно цитировать устаревшее поведение. Уточнения пользователя не обновляют документы индекса.

### Фактическая проверка

4 октября 2026 выполнены оба сценария через DeepSeek `deepseek-v4-flash`, индекс `d7864665-db3b-43cf-9c71-bb2e30365369`. Это прогоны прежнего режима поиска на каждом сообщении, до добавления `auto`; они не являются проверкой нового выбора режима. Отчёт: `data/rag-day25/462f7353-6887-4a22-a7d4-673f8115f94f.json`.

- 24/24 шагов завершились без технической ошибки, с сохранённой историей и новым поиском.
- 24/24 ответов содержат источники и дословные цитаты; проверка утверждений моделью пройдена.
- Исходная цель сохранена на всех 24 шагах, включая финальные напоминания после выхода первого сообщения из окна истории.
- Термины «контекст»/«сводка», structured, Asia/Omsk и изменения запрета библиотек/зависимостей сохранились; read-only календарь и запрет внешних баз остались действующими.
- Расход основного прогона: 372 499 токенов, включая вспомогательные вызовы.

Это **не «качество 24/24»**. Ручная проверка обнаружила, что в шаге 11 сценария фоновых задач модель дала восемь утверждений вместо запрошенных трёх пунктов. Проверка отдельных цитат этого не обнаруживала. После прогона добавлена отдельная проверка выполнения задачи **в рамках того же verifier-вызова**, с контролем количества пунктов и одной попыткой исправления. В первоначальном отчёте ещё нет `taskCheck`; его результаты не переобозначаются как результаты новой проверки. Также встречаются избыточные, хотя подтверждённые, подробности; правило краткости остаётся модельным, не абсолютной гарантией.

После перезапуска выполнены ещё **два отдельно согласованных повторных вопроса** в том же сценарии фоновых задач (ходы 13–14, без очистки истории). На первом получены ровно три пункта с цитатами о SQLite, захвате worker и MCP receipt; на втором — правильное напоминание ранней цели, read-only календаря и изменения запрета зависимостей. Проверяющий во втором обосновании ошибочно написал «три пункта», хотя в ответе четыре; этот вопрос не ограничивал их количество. Это ещё один пример ограничения LLM-проверки, а не основание считать текст обоснования безошибочным.

## Локальные тесты

### Проверка автоматического выбора режима

5 октября 2026 после включения `auto` у существующего агента выполнен отдельный согласованный прогон через DeepSeek. Пять сообщений: «Привет» → conversation без поиска; общее определение RAG → general без поиска; вопрос о поиске в нашем проекте → documents; «А где хранится этот индекс?» → documents с разрешённой ссылкой; напоминание цели → dialogue без поиска, с цитатой пользователя. Все пять ожидаемых маршрутов подтверждены, документальные ответы содержат цитаты, цель сохранена, в истории поисковый запрос есть только у двух документальных ответов. В Safari проверено отображение обычного ответа и пометок «Без поиска по документам».

Отчёт: `data/rag-day25/routing-9f624c86-6268-4925-9f43-ec6157d55404.json`, 42 021 токен успешного прогона. Перед ним первая попытка остановилась на приветствии: модель оставила question пустым, а прежняя схема это отклонила. В текущей версии исходное сообщение используется при пустом question в любом режиме, включая documents. Неуспешная попытка сохранена отдельно: `data/rag-day25/routing-2589a642-9fce-4e43-9fb5-15cdf318cde9.json`; её расход не входит в указанную сумму. Старые длинные сценарии не перепрогонялись.

Тесты проверяют сохранение ранней цели после 15 ходов при коротком окне, замену/отмену ограничений, поддельные цитаты памяти, изоляцию, восстановление после перезапуска, обычные HTTP `/run`/`/stream`, однократное сохранение, блокировку параллельного запроса, отмену и учёт токенов.
