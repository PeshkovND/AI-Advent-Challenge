# День 17 — MCP и Яндекс Календарь

`server/yandex-calendar-mcp-server.ts` реализует MCP-сервер над CalDAV-интерфейсом Яндекс Календаря. Он регистрирует четыре инструмента:

- `create_calendar_event` — создаёт событие;
- `get_calendar_events` — читает события в заданном временном диапазоне;
- `update_calendar_event` — заменяет поля события по UID;
- `delete_calendar_event` — удаляет событие по UID.

Все инструменты имеют Zod-схемы входных и структурированных выходных данных. Для обновления и удаления можно передать `etag`, полученный при чтении: это не даёт случайно перезаписать чужое изменение.

## Подготовка

1. В Яндекс ID создайте пароль приложения для «Календаря» или выпустите OAuth-токен с доступом к календарю.
2. Скопируйте `.env.example` в `.env` и задайте `YANDEX_CALDAV_EMAIL` и один секрет: `YANDEX_CALDAV_APP_PASSWORD` либо `YANDEX_CALDAV_OAUTH_TOKEN`.
3. Не добавляйте `.env` в Git.

## Вызов агентом

В приложении есть страница «Календарь» со свободным чатом. Агент отвечает на обычные вопросы через LLM, а при явном запросе на чтение, создание, изменение или удаление события сначала выбирает MCP-инструмент, вызывает его на сервере и формирует ответ из полученного результата. Пароль приложения остаётся на сервере в `.env`.

В начале агентского turn хост подключается к серверам из конфигурации и получает `tools/list`. Актуальные имена, описания и JSON Schema передаются модели через нативный OpenAI-совместимый параметр `tools`. Runtime namespace-ирует имя функции для модели по паре `serverId + toolName`, а затем маршрутизирует вызов обратно в исходный MCP-сервер. Поэтому инструменты разных серверов не конфликтуют, а добавление или переименование инструмента на MCP-сервере не требует изменения посредника или UI.

MCP — capability обычного агента, а не отдельный тип агента. В конфигурации `/api/agents` он включается так:

```json
{
  "mcp": {
    "enabled": true,
    "servers": ["yandex-calendar"]
  }
}
```

`servers` содержит только серверные идентификаторы из реестра приложения: команда запуска и секреты не могут попасть в пользовательскую конфигурацию.

### Безопасный контекст tool calling

Основной агент принимает решение о tool call с тем же подготовленным контекстом, что и при обычном ответе: системными инструкциями, памятью, резюме и историей диалога. MCP runtime не является вторым агентом: он получает актуальный каталог инструментов, передаёт его в тот же LLM-вызов, выполняет выбранные моделью вызовы и возвращает результаты.

Последняя пользовательская реплика остаётся последней в prompt и является единственной исполняемой командой. Предыдущие реплики имеют роль только разговорного контекста: старая фраза вроде «создай встречу» не может сама по себе повторно запустить действие в новом turn.

Перед основным ответом та же модель формирует структурированное решение `requiresTool`. Если текущая реплика требует доступного внешнего действия, runtime отправляет следующий запрос с `tool_choice: "required"`: модель обязана вернуть настоящий MCP-вызов, а не текстовое «готово». Это решение не является вторым агентом и не содержит отдельного набора контекста — оно защищает исполнение в основном agent loop.

Календарная страница передаёт `conversationId` и безопасный `clientContext.timeZone` для текущего видимого чата. Это не создаёт другого типа агента: используется та же конфигурация `day17-mcp-agent`, но его память и история изолированы по сессиям. Runtime использует часовой пояс браузера для текущей даты и относительных дат; явный пояс из сообщения пользователя имеет приоритет. Страница Day 18 использует этого же агента с другой сессией: ему добавлен Scheduler MCP, поэтому один агент умеет и работать с событиями, и создавать отложенные задачи. Поэтому накопленные сообщения из старого чата не становятся скрытым контекстом нового диалога.

После успешного MCP-вызова `AgentService` сохраняет до четырёх его структурированных результатов отдельно от переписки. В следующем turn они передаются только как справочные, непригодные для исполнения данные. Это позволяет обработать «переименуй его» по UID события, созданного в предыдущем turn, но не позволяет модели повторно исполнять прошлые запросы. Утверждать выполнение операции агент может только после результата инструмента в текущем turn.

Tool calling отправляется в API выбранного провайдера: DeepSeek, OpenRouter или Hugging Face Inference Providers. MCP доступен всем трём, если выбранная модель поддерживает function calling.

Сервер подготавливает обычного агента `day17-mcp-agent` при запуске. Диалог запускается через стандартный `POST /api/agents/day17-mcp-agent/run`; отдельной ручки или отдельного класса агента для календаря нет. В его конфигурации два MCP-сервера: `yandex-calendar` и `scheduler`.

Под ответом в чате выводится trace фактически выполненных MCP-инструментов, например `create_calendar_event ✓`. Он строится из поля `mcpToolCalls`, которое вернул сервер, поэтому не зависит от текста, сгенерированного моделью. Параметры вызовов и данные календаря в trace не показываются.

Яндекс предоставляет доступ к календарю через CalDAV по адресу `https://caldav.yandex.ru`; `events-default` — основной календарь пользователя.

При сетевом обрыве до TLS-рукопожатия сервер делает ограниченные повторные попытки и для записи: в этот момент HTTP-запрос ещё не был отправлен, поэтому повтор не создаёт дубль. Ошибки после установленного соединения для операций изменения не повторяются автоматически.

## Сквозная проверка

После изменений MCP-flow запускайте `RUN_CALENDAR_E2E=1 npm run test:mcp:e2e` при работающем локальном API. Тест создаёт уникальное событие через обычную ручку агента, проверяет его отдельным read-only вызовом CalDAV, переименовывает, снова проверяет, удаляет и подтверждает отсутствие. В `finally` он также пытается удалить тестовое событие и временного агента при неудаче. Команда намеренно требует явный флаг: она изменяет реальный календарь.
