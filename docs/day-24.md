# День 24 — источники, цитаты и отказ при слабом контексте

Режим включается у обычного агента через конфигурацию. Создание, обновление, `/run` и `/stream` — те же, что для других агентов. Отдельной страницы или кнопок демонстрации нет: на существующей странице «RAG» все три RAG-агента используют обязательные цитаты и проверку смысла. Агент без RAG не изменён.

## Конфигурация

```json
{
  "rag": {
    "enabled": true,
    "strategy": "structured",
    "candidateTopK": 20,
    "topK": 4,
    "queryRewrite": true,
    "rerank": { "enabled": true, "minRelevance": 2 },
    "grounding": { "enabled": true },
    "indexRunId": "ID существующего индекса"
  }
}
```

`grounding.enabled: false` или отсутствие этого поля сохраняет поведение Day 22/23. В форме создания агента есть соответствующий переключатель. Цитаты независимы от стратегии поиска: базовые `structured` и `fixed` используют прежний cosine top-4 без rewrite, реранкинга или нового порога similarity, а затем проверяют ответ и цитаты. Если найденные фрагменты не подтверждают ответ, генератор возвращает `unknown` либо проверяющий отвергает утверждения.

У улучшенного RAG сохранён порог реранкера `minRelevance: 2`. Он применяется **до** генерации ответа; уровень 2 означает «содержит часть необходимых фактов», 3 — «прямой ответ или существенная часть». Это категории полезности, не вероятности истинности. При явно заданном `minSimilarity` также применяется cosine-порог. Эти фильтры не являются обязательными для включения цитат.

Контракт предназначен для ответов по документам. Конфигурации с MCP-действиями, `taskMachine` или stop-последовательностями отклоняются, потому что у них другой контракт ответа/источник доказательств. Память, история, контекстные стратегии и инварианты сохраняют обычный путь агента. Слишком маленький лимит символов даёт ошибку, а не обрезанные цитаты.

## Как формируется ответ

1. Поиск соответствует конфигу агента: у `structured`/`fixed` обычный cosine top-4; у улучшенного — rewrite, эмбеддинги, объединение поиска и реранкинг как в Day 23, максимум 4 прошедших порог чанка.
2. Если чанков нет, сервер без вызова генератора возвращает **«Не знаю»** и просьбу уточнить компонент/документ или предоставить источник. `sources`, `citations` и `claims` пусты: создавать цитаты при отсутствии доказательств запрещено.
3. При наличии контекста модель возвращает строгий JSON: `status: answered` и максимум 8 утверждений `claims`. Каждое утверждение содержит одну или несколько ссылок `{chunkId, quote}`. Либо модель возвращает `status: unknown`, если контекст не отвечает на вопрос.
4. Сервер проверяет JSON, существование каждого ID **среди отобранных чанков** и дословное вхождение каждой цитаты в текст. Цитаты — непрерывные фрагменты 12–1200 символов; никакого fuzzy matching, подстановки пересказа или разворачивания многоточий. Путь файла и раздел восстанавливаются из индекса, а не принимаются от модели.
5. Отдельный вызов той же LLM видит исходный вопрос, утверждения и только их цитаты. Он проверяет смысловую поддержку каждого утверждения: отрицания, числа, условия и порядок приоритетов. Совпадение темы недостаточно.
6. Невалидная цитата или неподтверждённое утверждение допускают одну попытку генерации исправленного ответа. Исправление заново проходит обе проверки. При повторной смысловой неподтверждённости возвращается «Не знаю» с уточнением. Постоянно невалидный JSON, сбой API или некорректный результат проверяющего — явная техническая ошибка, не ложный отказ «данных нет».
7. Только после проверок сервер собирает читаемый ответ из утверждений, номера ссылок и блоки «Источники и цитаты». В обычный чат и историю идёт этот проверенный текст. Streaming в строгом режиме буферизуется: неподтверждённые токены не отправляются клиенту.

Ответ на слабый контекст — намеренно фиксированное безопасное сообщение сервера. Ответы с доказательствами — утверждения модели; текст цитат тоже выбирает модель, а сервер лишь проверяет его и подставляет настоящие метаданные. Ожидания контрольных вопросов не передаются генератору, реранкеру или проверяющему.

## API-результат

`output` содержит готовый текст с источниками и цитатами. `rag.sources` — найденный контекст, как раньше. Дополнительно `rag.grounding` содержит:

- `status`: `answered` / `unknown`;
- `answer`: текст только из проверенных утверждений;
- `sources`: **использованные** источники `{source, section, chunkId}`;
- `citations`: `{id, source, section, chunkId, quote}`;
- `claims`: `{id, text, citationIds}`;
- `clarification` и `reason` для отказа (`weak-context`, `insufficient-evidence`, `unsupported-answer`);
- `verification`: результат и обоснования смысловой проверки;
- `usage`: точная сумма токенов генерации, проверки и исправлений.

При `outputPolicy.format: json` полный контракт находится также в JSON-строке `output`. Общие метрики агента включают rewrite, реранкинг, генерацию и проверку без двойного подсчёта. У базовых RAG-агентов обычно два вызова DeepSeek (генерация и проверка), у улучшенного — четыре; исправления добавляют вызовы. Отказ по порогу не запускает генератор и проверяющий, но стоимость уже выполненных rewrite/реранкинга учитывается. Если сам генератор возвращает `unknown`, проверяющий не вызывается.

## Демонстрация

Откройте «RAG», нажмите существующую кнопку **Создать или обновить агентов**, если она доступна, и запустите набор из 11 вопросов: исходные 10 плюс вопрос №11 про схему репликации Redis и количество реплик в проекте. Его нет в базе; ожидается «Не знаю», просьба уточнить и пустые использованные источники/цитаты у всех RAG-агентов. Это тот же вопрос, который уже дал корректный отказ у улучшенного RAG в контрольном прогоне (там ID 14). Отдельного обработчика или подставленного ответа для него нет: все четыре агента получают обычный вопрос через `/run`. Без RAG модель может объяснить типичный подход, но не знает конфигурацию этого проекта.

Источники и дословные цитаты отображаются прямо внутри ответов всех трёх RAG-агентов. Старые ответы сохраняются; ответы без grounding помечены «Сохранённый ответ — без обязательных цитат. Нужен новый прогон», пока не выполнен новый прогон. Уже полученные проверенные ответы не переобозначаются как устаревшие. Новых кнопок повторения ошибок, отдельных экранов и таблиц настройки нет. CLI-проверка по-прежнему проверяет улучшенного агента на исходных 10 вопросах либо 12 с `--extended`.

## Контрольный прогон

```bash
npm run dev
# 10 исходных вопросов; реальные вызовы обычного агентного API
npm run rag:check-grounding
# + два вопроса вне базы (GPU training и Redis replication)
npm run rag:check-grounding -- --extended
```

Скрипт обновляет конфигурацию существующего четвёртого агента `day23-full` (его ID сохранён для совместимости), закрепляет текущий индекс и вызывает `/api/agents/:id/run` с отдельным `conversationId` для каждого вопроса. Историю других агентов и браузерные результаты не меняет. Итоги и полные ответы записываются в `data/rag-day24/<uuid>.json`, эта папка не коммитится. Наличие источников, наличие цитат, точное вхождение и результат смысловой проверки фиксируются отдельно для каждого вопроса. Контрольные ожидания тоже включены для ручной проверки полноты ответа, но не передаются агенту.

Для вопросов вне базы правильный результат — отказ с уточнением и **отсутствием** цитат; они не включаются в знаменатель «источники/цитаты в 10 ответах». Отказ на вопрос, ответ на который есть в базе, считается неуспешной проверкой, а не положительным результатом.

## Ограничения

Дословность цитат и корректность метаданных проверяются детерминированно. Смысловая поддержка — оценка LLM отдельным вызовом, не математическая гарантия. Генератор и проверяющий используют одну модель, поэтому возможны коррелированные ошибки. Проверка каждого утверждения не гарантирует полноту всего ответа. Точность самих документов и актуальность индекса — отдельные вопросы: текущий индекс содержит снимок проекта до Day 23, и дословная цитата из него может описывать старую реализацию. Индекс намеренно не меняется между режимами сравнения.
