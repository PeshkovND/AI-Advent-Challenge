# День 22 — первый RAG-запрос

RAG встроен в обычного агента. Агент создаётся через `POST /api/agents` и вызывается через существующие `POST /api/agents/:agentId/run` и `POST /api/agents/:agentId/stream`. Режим задаётся конфигурацией агента:

```json
{
  "rag": { "enabled": true, "strategy": "structured", "topK": 4 }
}
```

Если `rag` не включён, вопрос идёт к той же LLM без поиска. Такой агент отвечает из общих знаний; если вопрос касается деталей именно этого проекта, он должен отделять типичное объяснение от неподтверждённых фактов. Настройка сохраняется в обычном реестре агентов и доступна в разделе «Агенты». Для учебного сравнения используются три агента с одной моделью `deepseek-v4-flash`, одинаковым системным промптом и `temperature: 0`: без RAG, с RAG `structured` и с RAG `fixed`. У двух последних одинаковый `topK: 4`; отличается только стратегия разбиения.

## Путь одного RAG-запроса

1. Агент получает исходный вопрос через свой стандартный `/run` или `/stream`.
2. Ollama моделью, записанной в последнем индексе Day 21, строит эмбеддинг вопроса.
3. SQLite-индекс возвращает четыре чанка выбранной в конфигурации стратегии (`structured` или `fixed`) с наибольшей cosine similarity. Вопрос кодируется с профилем того запуска индекса, в котором были созданы векторы документов.
4. Текст чанков и их `source`, `section`, `chunk_id` добавляются к сообщениям LLM как отдельный контекст. Исходный вопрос остаётся исходным вопросом, а в историю диалога не сохраняется копия найденных документов.
5. Обычный агент формирует ответ. Результат включает список найденных источников и идентификатор использованного запуска индекса. Агенту предлагается помечать утверждения ссылками `[1]`, `[2]` и сообщать, если контекста недостаточно.

Недоступный Ollama, пустой индекс и отсутствие выбранной стратегии дают явную ошибку. Найденные фрагменты считаются данными, а не инструкциями.

## Демонстрация в React

Запустите приложение `npm run dev` и откройте страницу **RAG** в боковом меню.

1. Нажмите «Создать или обновить агентов через /api/agents». Это обычные записи в реестре; они появятся также на странице «Агенты». Если агенты уже созданы, их конфигурации обновятся без удаления истории.
2. Нажмите «Получить ответы на все 10 вопросов». Страница последовательно отправит каждый вопрос всем трём агентам через `/run`.
3. Для каждого вопроса страница покажет рядом ожидаемый результат, ответ без RAG, ответ с `structured` и ответ с `fixed`. Ожидаемые источники видны сразу; контрольные фрагменты с ответом и фактически найденные фрагменты можно раскрыть отдельно. У RAG-ответов есть индикатор, сколько контрольных фрагментов попало в поиск.
4. «Скачать результаты JSON» сохранит вопросы, ожидания, три фактических ответа и найденные источники. «Очистить тесты агентов» после подтверждения удалит историю всех диалогов трёх агентов и результаты на странице, но сохранит конфигурации агентов и RAG-индекс. После этого можно провести новый прогон.

Один сравнительный запуск использует новый `conversationId`, поэтому предыдущие вопросы не меняют контекст сравнения. Генерация требует доступного DeepSeek API; RAG-поиск использует локальный Ollama. При первом запуске или после изменения документов обновите индекс командой `npm run rag:index`.

Важная граница данных: при сравнении вопросы уходят в DeepSeek API, а для двух RAG-агентов дополнительно отправляются найденные фрагменты локальных документов. Страница предупреждает об этом до запуска.

## 10 контрольных вопросов

| № | Вопрос | Ожидаемые факты | Ожидаемые источники |
| ---: | --- | --- | --- |
| 1 | Что хранится в `data/scheduler.sqlite` и как worker забирает задачу? | Задачи, запуски, события, heartbeat; `BEGIN IMMEDIATE` и блокировка. | `docs/day-18.md` |
| 2 | Что происходит с пропущенными запусками после сна компьютера? | Одна просроченная проверка; интервалы подряд не воспроизводятся. | `docs/day-18.md` |
| 3 | Какие три слоя памяти есть у агента? | Short-term, working и long-term с разными сроками и назначением. | `docs/day-11.md` |
| 4 | Как маршрутизируется Telegram tool среди MCP-серверов? | Квалифицированное имя, `serverId`, вызов нужного MCP-клиента. | `docs/day-20.md` |
| 5 | Почему фоновый агент Day 20 не создаёт события при `serverToolAccess: read-only`? | Инструменты записи не выдаются фоновому агенту. | `docs/day-20.md`, `docs/day-18.md` |
| 6 | Как определяется часовой пояс новой периодической задачи? | Приоритет: указание пользователя, пояс браузера, `AGENT_TIME_ZONE`. | `docs/day-18.md` |
| 7 | Какие стратегии разбиения реализованы в Day 21? | Fixed 200 слов и overlap 40; structured по заголовкам/файлам. | `docs/day-21.md` |
| 8 | Какие метаданные хранятся у RAG-чанка? | `source`, `title`, `section`, `chunk_id`, стратегия и порядковый номер. | `docs/day-21.md` |
| 9 | Как ищет локальный RAG-индекс? | Эмбеддинг вопроса через Ollama, cosine similarity по векторам SQLite. | `docs/day-21.md` |
| 10 | Что проверяется перед сохранением успешной фоновой сводки? | Успешный MCP receipt; одной декларации модели недостаточно. | `docs/day-18.md` |

Ожидаемые факты, источники и фрагменты с ответом зафиксированы до запуска LLM. Локальная команда `npm run rag:check-questions` проверяет оба RAG-режима: для каждого вопроса показывает позицию каждого контрольного фрагмента и считает успехом только попадание **всех** таких фрагментов в top 4. Прежняя проверка «нужный файл найден» давала вводящие в заблуждение 10/10: нужный файл мог попасть в выдачу не тем разделом. Проверка поиска не оценивает сгенерированные ответы — их сравнивают с ожиданиями на странице.

Локальный контрольный прогон после перехода на многоязычную модель, добавления префиксов и заголовков к эмбеддингам и удаления проверочных файлов из корпуса: `fixed` — **10/10**, `structured` — **9/10** по попаданию фрагментов в top 4. До изменений было соответственно **4/10** и **6/10**. Это сравнение работающих версий целиком, а не изолированный эксперимент с одной переменной: корпус за время разработки тоже изменился. Для вопроса №9 нужный фрагмент у `structured` пока остаётся на 7-м месте. Попадание фрагмента не гарантирует правильный ответ LLM.

## Проверки

```bash
npm run test:rag:agent
npm run test:rag
npm run rag:check-questions
npm run typecheck
npm run build
```

Тесты проверяют, что обычный агент добавляет RAG-контекст при `/run` и `/stream`, возвращает метаданные источников, сохраняет исходный вопрос и не обращается к индексу при выключенном RAG.
