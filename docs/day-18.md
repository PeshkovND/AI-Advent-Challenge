# День 18 — планировщик и фоновые задачи

## Что сделано

Day 18 расширяет агента из Day 17 — `day17-mcp-agent`. В одном чате можно создать, изменить, удалить или посмотреть событие Яндекс Календаря, а также поставить регулярную календарную сводку. Новый тип управляющего агента для планировщика не создаётся. Например: «Каждый будний день в 09:00 формируй сводку событий на неделю, но только в дни с чётной датой».

Агент планировщика переводит **периодичность** в cron и создаёт задачу через Scheduler MCP. Полный исходный текст условия сохраняется без попытки свести его к ограниченной JSON-схеме. При каждом запуске фоновый агент получает этот текст, актуальную дату и время и принимает структурированное решение:

```json
{
  "status": "success | skipped",
  "reason": "почему задача выполнена или пропущена",
  "summary": "сводка при success"
}
```

Поэтому условие «только по будням», «только при чётной дате», «только если есть события» или комбинация условий оцениваются непосредственно в день запуска. Расписание отвечает за то, **когда проверять**, а естественный язык — **нужно ли выполнять и что именно делать**.

## MCP-инструменты

`scheduler-mcp-server.ts` регистрирует:

- `create_scheduled_agent_task` — сохраняет периодическую задачу;
- `list_scheduled_tasks` — показывает задачи;
- `get_scheduled_task_result` — возвращает последние результаты и историю;
- `run_scheduled_task_now` — ставит ручной запуск в очередь;
- `delete_scheduled_task` — отменяет задачу и её журнал.

При создании нельзя передать произвольный `agentId`: Scheduler MCP всегда закрепляет задачу за `day18-scheduler-agent`.

## Часовые пояса

Каждая задача хранит свой IANA-часовой пояс, например `Asia/Omsk` или `Europe/Moscow`. При каждом сообщении интерфейс передаёт определённый браузером пояс в `clientContext.timeZone`. Если пользователь не назвал иной пояс, агент использует этот пояс для относительных дат и для новой задачи. Runtime передаёт его также дочернему MCP-процессу как дефолт схемы, поэтому он применяется даже при пропущенном необязательном поле `timezone`. Явно названный пользователем город или пояс всегда имеет приоритет. `AGENT_TIME_ZONE` из `.env` (при отсутствии — `Asia/Omsk`) остаётся только запасным вариантом для запросов без браузерного контекста и для фонового процесса. Агент называет выбранный пояс в ответе. Изменение настройки или перемещение пользователя не меняет уже сохранённые задачи. Интерфейс форматирует следующий запуск, журнал и результат в часовом поясе конкретной задачи.

## Безопасность исполнения

Фоновый агент имеет `toolAccess: "read-only"`. Runtime оставляет ему только MCP-инструменты с `annotations.readOnlyHint: true`; у календаря это `get_calendar_events`. Создание, изменение и удаление событий не попадают в каталог инструментов фонового агента даже при ошибке в prompt.

Перед сохранением результата executor требует успешный MCP receipt для `status: "success"`. Он не позволит записать неподтверждённую сводку, если модель просто заявила, что прочитала календарь.

## Хранение и worker

SQLite (`data/scheduler.sqlite` на компьютере, путь можно задать через `SCHEDULER_DB_PATH`) хранит:

- задачи и исходные инструкции;
- очереди и результаты запусков;
- пошаговые события запуска;
- heartbeat worker.

Планировщик опрашивает очередь каждые 30 секунд, берёт задачу атомарно через `BEGIN IMMEDIATE`, ставит блокировку на пять минут, пишет события и сохраняет итог. WAL и `busy_timeout` позволяют API и дочернему Scheduler MCP использовать одну базу. После аварийного перезапуска просроченные блокировки освобождаются, а прерванные запуски получают статус `error`. Проверка блокировок выполняется при каждом опросе, в том числе если сервер перезапущен до истечения пяти минут.

Планировщик работает внутри основного Node-процесса и напрямую вызывает общий `AgentService`. API начинает слушать только после подготовки агентов; планировщик стартует после успешного открытия порта. Второй сервер и отдельный HTTP-вызов для фоновой задачи не нужны. Сессия задачи изолирована ключом `scheduled:<job_id>`. При обычной остановке (`Ctrl+C`) сервер перестаёт брать новые задачи и ждёт сохранения результата текущего запуска.

Браузер можно закрыть: задачи продолжат выполняться, пока сервер запущен. Если компьютер выключен или спит, выполнение приостанавливается. После возвращения планировщик выполнит одну просроченную проверку каждой задачи с актуальными датой и условиями и рассчитает следующий запуск. Все пропущенные интервалы подряд не воспроизводятся. Уже начатый и аварийно прерванный запуск автоматически не повторяется.

При ошибке CalDAV текущий запуск завершится с `error`, задача останется активной. Следующая попытка — по расписанию или по кнопке «Запустить сейчас». Повтор всего фонового запуска с задержкой пока не реализован.

## Демонстрация

На странице «Сводки» есть:

- чат с агентом планировщика;
- активные задачи и следующая дата запуска;
- актуальный статус планировщика;
- последняя сводка;
- ручной запуск и удаление;
- журнал очереди, запуска агента и результата.

Для демонстрации:

1. Запустите приложение и откройте «Сводки».
2. Напишите: «Каждую минуту формируй сводку событий на ближайшую неделю».
3. Проверьте в ответе чата успешный вызов `create_scheduled_agent_task` и появление карточки.
4. Дождитесь ближайшей минуты или нажмите «Запустить сейчас» (очередь проверяется раз в 30 секунд).
5. Страница автоматически обновляется каждые пять секунд: появятся статус, сводка и журнал. «Обновить» позволяет проверить данные немедленно.
6. Для демонстрации условий создайте задачу с явно ложным условием, например «Формируй сводку только по воскресеньям» в другой день. Результат должен быть `skipped` с объяснением.
7. Перезапустите приложение: задачи и журнал останутся. После демонстрации удалите минутную задачу, чтобы она не расходовала токены дальше.

Полученные результаты также доступны через MCP-инструмент `get_scheduled_task_result`. Сам факт запуска хранится отдельно от текста сводки.

## Проверки

Без внешних вызовов:

```bash
SCHEDULER_DB_PATH="$(mktemp -d)/scheduler.sqlite" npm run test:scheduler:smoke
npm run typecheck
npm run build
npm run test:scheduler:local
```

Smoke-тест использует только временную SQLite, подставной executor и дочерний Scheduler MCP. Он проверяет ручную очередь, атомарную привязку запуска к задаче, журнал событий и передачу `SCHEDULER_DB_PATH` в MCP-процесс. Локальные тесты отдельно проверяют остановку/перезапуск планировщика, сохранность задач и запуск приложения на loopback-адресе. Эти проверки не вызывают LLM и CalDAV.

## Локальный запуск

Используйте Node.js 24+ (нужен встроенный `node:sqlite`). Установите зависимости и создайте `.env`, только если его ещё нет:

```bash
npm install
# При первой настройке, если .env ещё нет:
cp .env.example .env
```

Заполните `DEEPSEEK_API_KEY`, `YANDEX_CALDAV_EMAIL` и пароль приложения либо OAuth-токен. `AGENT_TIME_ZONE` по умолчанию в примере — `Asia/Omsk`. Существующий `.env` и каталог `data/` при переходе на локальную версию менять не нужно.

Для работы и демонстрации одной командой:

```bash
npm start
```

Команда собирает интерфейс и запускает API с планировщиком. Откройте `http://127.0.0.1:8787` (либо порт из `PORT`). Повторный запуск без пересборки: `npm run start:server`.

Для разработки: `npm run dev`. Vite показывает интерфейс на `http://127.0.0.1:5173`, а запросы `/api` перенаправляет в тот же локальный сервер с планировщиком. `npm run preview` отдельно запускает только предпросмотр интерфейса и не заменяет `npm start`.

И API, и Vite слушают `127.0.0.1`: приложение доступно с этого компьютера, без публикации в локальную сеть. Домен, Docker, Caddy и Basic Auth больше не нужны. Это не офлайн-режим: для LLM и Яндекс Календаря по-прежнему нужен интернет. Не запускайте одновременно несколько копий API с одним каталогом данных.

Задачи и сводки сохраняются в `data/scheduler.sqlite`, конфигурации и история агентов — в `data/agent-state.json`. Для сохранности держите каталог `data/` при обновлении проекта; он, как и `.env`, исключён из Git.
