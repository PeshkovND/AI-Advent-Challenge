# День 35. MyFamily Release Copilot

Статус: реализован первый сквозной сценарий. Ниже описана концепция всего проекта; фактический состав первой версии и её запуск — в конце документа.

## Задача

Автоматизировать подготовку релиза MyFamily. Перед выпуском разработчику приходится вручную вспоминать изменения, сопоставлять их с обращениями пользователей, проверять проблемные сценарии, обновлять документацию и писать описание версии. Информация уже есть в Git, коде, документации и тикетах, но её нужно собрать в один результат.

Release Copilot получает выбранный локальный репозиторий, базовый и целевой Git ref и номер версии. На выходе — рабочее досье релиза: подтверждённые изменения, риски, план проверок, черновик release notes и предлагаемые обновления документации.

Первый целевой проект — настоящий MyFamily, с которым уже работали в днях 31–34. Приложение выделено в самостоятельный React/TypeScript-проект `release-copilot/` со своим сервером, интерфейсом, зависимостями и данными.

## Пользовательский сценарий

1. Выбрать папку MyFamily, предыдущий тег или commit, целевую ветку и обозначение версии. Если тегов нет, указать два commit.
2. Нажать «Подготовить релиз». Сервис фиксирует оба SHA и собирает реальные diff, изменённые файлы, документацию и выбранные обращения поддержки.
3. Получить список изменений с доказательствами, потенциальные проблемы и связанные обращения. Связь тикета и правки — предположение AI до проверки; статус «исправлено» автоматически не выставляется.
4. Просмотреть конкретный план ручного тестирования: предусловия, действия и ожидаемый результат. Например, изменение авторизации требует проверить вход, выход и восстановление сессии.
5. Проверить черновик «Что нового», внутренний changelog и diff документации. Материалы для пользователей отделены от внутренних технических сведений и содержимого тикетов.
6. Отметить результаты ручных проверок и скачать пакет релиза. Изменения документации применяются отдельным действием после просмотра diff.

## Как участвует AI

| Этап | Работа AI | Основание результата |
| --- | --- | --- |
| Анализ изменений | Объясняет влияние diff на пользовательские сценарии | Зафиксированные SHA, пути и строки кода |
| Поиск контекста | Находит правила продукта и связанные модули | RAG по документации, поиск и чтение файлов |
| Сопоставление поддержки | Предлагает, какие обращения могут относиться к изменению | ID тикета, сообщения и фрагменты diff |
| Оценка рисков | Выделяет возможные регрессии и вопросы для разработчика | AI-ревью с явным обозначением предположений |
| План проверок | Формирует проверяемые сценарии под изменённое поведение | Изменения и доступные требования |
| Подготовка материалов | Пишет release notes и предлагает правки справки | Подтверждённые изменения и прочитанная документация |

Git, файловые операции, очередь, сохранение и проверка ссылок выполняются обычным кодом. Решение о готовности релиза учитывает результаты проверок; положительный ответ модели сам по себе не означает готовность к выпуску. Неполный анализ или недоступный источник явно отражаются в отчёте.

## Демонстрация и критерии результата

Демонстрационный запрос: «Подготовь релиз MyFamily между этими двумя commit. Объясни, что изменилось для пользователя, какие обращения могут быть затронуты и что проверить перед выпуском».

Готовность первой версии проверяется на настоящей паре commit MyFamily:

1. В отчёте указаны фактические SHA, набор файлов и ограничения покрытия.
2. Описания изменений и рекомендации снабжены проверяемыми источниками; предположения обозначены отдельно.
3. Отсутствие подходящих тикетов, модели или документации показано явно и не заменено выдуманными результатами.
4. Ручная проверка имеет отдельный статус; генерация плана не помечает её выполненной.
5. Состояние запуска и подготовленные материалы доступны после перезапуска приложения.
6. Экспорт содержит материалы по выбранному диапазону; пользовательские release notes не включают персональные данные тикетов.
7. Diff документации можно просмотреть; применение проверяет, что исходные файлы не изменились после подготовки.

## Порядок реализации

Сначала — вертикальный сценарий «выбрать два commit → получить подтверждённую сводку → сохранить release notes». Затем — риски и ручные проверки, подключение тикетов, правки документации и итоговый экспорт. Каждый этап проверяется на реальном репозитории MyFamily.

## Реализованная версия

Отдельное приложение **Release Copilot** (`http://127.0.0.1:8796`) использует собственный каталог локальных проектов и выбор папки. Пользователь задаёт номер версии, базовый и целевой Git ref, выбирает Ollama или DeepSeek. Сервис закрепляет оба SHA до постановки в очередь и сравнивает именно их деревья; PR-ревью дня 32 сохраняет прежнее сравнение от merge-base. Checkout, файлы приложения и ветки выбранного проекта не меняются. Незакоммиченные файлы не анализируются.

На каждый файл модель получает полный diff, полное содержимое и контекст документации/кода baseline через существующий лексический RAG. Это поиск по снимку Git, а не по потенциально изменённым документам на диске; Ollama embeddings для него не нужны. Модель возвращает сводку, пользовательскую заметку, риски и конкретные ручные проверки. Код проверяет JSON и привязки к изменённым строкам. Второй вызов той же модели независимо проверяет смысл всех выводов и выполнимость проверок. Замечания возвращаются автору, до трёх попыток; непроверенный материал файла не сохраняется как готовый. Эта проверка вероятностная и не заменяет просмотр разработчиком.

Один фоновый worker обрабатывает сохранённую очередь последовательно. Обновление страницы и закрытие браузера не отменяют запуск. При остановке сервера активный запуск получает ошибку; после аварийного завершения это определяется при следующем старте. Повтор сохраняет SHA и перезапускает анализ; прежние ручные отметки сбрасываются. Отмена не позволяет позднему ответу модели записать результат.

История, шаг анализа, метрики, источники, ручные статусы и заметки сохраняются в `release-copilot/data/release-runs/<uuid>/run.json`. Для завершённого анализа в том же каталоге создаются четыре материала: `release-notes.md`, `changelog.md`, `test-plan.md`, `readiness.json`. Файлы можно скачать отдельно или вместе в ZIP-архиве `bundle.zip`. Архив формируется при скачивании и включает актуальные статусы и заметки ручных проверок.

Состояния: `queued` → `collecting` → `analyzing` → `awaiting_checks` → `ready`; отдельно `failed` и `cancelled`. `ready` означает готовность проверенных пользователем материалов, не публикацию приложения. Нужны полное покрытие, подтверждение выводов и статус `passed` у всех ручных проверок. Изменение любого результата может вернуть `awaiting_checks`. Неполный анализ можно экспортировать как черновик, ограничения перечислены явно.

### Запуск отдельного приложения

```bash
cd release-copilot
npm ci
cp .env.example .env
ollama pull qwen3.5:9b
npm run build
npm start
# http://127.0.0.1:8796
```

Разработка: `npm run dev` в каталоге приложения, интерфейс на `5176`, API на `8796`. Для облачной модели задайте `DEEPSEEK_API_KEY` в собственном `.env`. Модель задаётся через `RELEASE_LOCAL_MODEL` (по умолчанию `qwen3.5:9b`).

Все исполняемые модули находятся внутри `release-copilot/`, без импортов файлов DeepChat. Сервис не запускает чат, поддержку или MCP-планировщик. Код чтения Git, chunking, лексического RAG, транспорта моделей и проверки источников выделен из предыдущих заданий в собственные модули.

Каталог проектов и два прежних запуска перенесены командой `npm run import:deepchat -- --from ..`; исходные данные сохранены. При повторном импорте существующие результаты не перезаписываются. Ключи из старого `.env` не копируются. [Полная инструкция и объяснение процесса](../release-copilot/README.md).

При смысловой проверке каждый пункт получает собственные цитаты. Для CI и документации код запрещает пользовательскую release note, а для изменения только `uses`/pin в workflow — риски о недоступной реализации зависимости. Небольшая замена цитируется целиком с обеих сторон; в большом diff модель должна указать обе стороны сама.

### Ограничения и следующие этапы

Прежние ограничения 30 изменённых файлов, 10 КБ diff, 4 КБ содержимого и 18 КБ доказательств сняты: изменённые текстовые файлы и diff читаются целиком. Корпус RAG ограничен 400 документами/4 МБ; закрытые пути, lock-файлы, бинарные объекты и неподдерживаемые форматы пропускаются. Если полный запрос не помещается в контекст локальной Ollama, файл получает явную ошибку, без обрезки; DeepSeek использует контекст своего API. Точные ошибки структуры ответа сохраняются по попыткам и возвращаются модели для исправления; пользователь видит краткую причину, без текста системного промпта. Отбор контекста RAG сам по себе не доказывает полноту требований. Ссылка на реальную строку не гарантирует правильную трактовку; даже второй модельный вызов может пропустить ошибку.

Пока не реализованы сопоставление тикетов, подготовка/apply правок документации, Xcode-проверки, публикация в App Store или GitHub. Модель не исполняет команды из исходников. Интерфейс ручных результатов фиксирует сведения пользователя; он не проверяет запуск тестов внешним инструментом.

### Проверки

`npm run test:releases` проверяет реальные Git-снимки и HTTP с контролируемой моделью: точное сравнение commit, исключение незакоммиченных/закрытых файлов, проверку цитат и смысловой отказ, очередь после перезапуска, отмену, повтор, ручные статусы, неполное покрытие и экспорт. Реальные модельные прогоны учитываются отдельно.

### Исправление анализа большого diff (19 октября 2026)

На диапазоне MyFamily `589ce98dfbe28cf6ee7e87e8035bf98deda63a19 → 4a56dcd5f4c2dd5f688379bf10948aba7ac5f6d0` воспроизведён отказ `Account.swift`: DeepSeek вернул корректный JSON с 12 ссылками в `summary.evidenceIds`, а прежняя схема допускала не более 8. Облачная модель получала только пример формы ответа без точных ограничений схемы; повторные попытки сообщали общий текст «Неверный JSON или схема ответа», не называя ошибочное поле. Служебная подсказка исправления попадала в пользовательское сообщение.

Убран искусственный максимум количества цитат; каждая цитата по-прежнему обязана существовать в снимке Git, а выводы проходят независимую проверку. DeepSeek получает полную схему анализа и проверки. Повторная попытка получает предыдущий ответ и точные ошибки полей; техническая диагностика сохраняется отдельно от пользовательского текста.

### Проверка взаимодействий файлов

После анализа отдельных файлов новые запуски автоматически проверяют связанные реализации, прямых потребителей и тесты из обоих снимков Git. Граф кандидатов строится по символам и относительным импортам; AI сопоставляет совместное поведение и переоценивает гипотезы файлов (`confirmed` / `dismissed` / `uncertain`). Межфайловые выводы и сценарии должны цитировать минимум два файла и изменённую строку, затем проходят независимую проверку по этим цитатам. Граф используется как подсказка, не запрещает связь, доказанную самим кодом. Гипотеза о внутреннем поведении helper может быть снята его собственной реализацией, без искусственных цитат вызывающего файла.

Существующие запуски дополняются через вкладку «Связи файлов» или `POST /api/releases/runs/:id/impact`, без повторной генерации анализа файлов. Ручные статусы и заметки сохраняются; новые общие сценарии проверяются отдельно. Ошибка этапа делает покрытие частичным и блокирует готовность. Выводы, оценки рисков и сценарии включены в прежний ZIP из четырёх материалов.

Поиск связей эвристический: неоднозначные имена, динамические вызовы и некоторые языковые конструкции могут быть пропущены. Это не заменяет компилятор или тесты. На диапазоне MyFamily предварительный просмотр двух снимков нашёл 107 исходных файлов, 45 файлов контекста и 72 связи-кандидата, включая `AuthService.swift → ProfileCompletion.swift` по `isComplete`.

Независимая модельная проверка приняла 34 пункта. Цитаты отдельно сверены с Git blob, исходные результаты девяти файлов и ручные заметки сохранены без изменения.
