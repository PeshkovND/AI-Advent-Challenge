# День 14. Инварианты и ограничения состояния

Инварианты — это жёсткие правила агента, сохранённые отдельно от истории
диалога. Они задаются при создании или обновлении агента и не сбрасываются при
новой задаче, паузе, summary-сжатии, смене ветки контекста или очистке истории.

```ts
{
  invariants: {
    enabled: true,
    items: [
      {
        id: 'swiftui',
        title: 'UI-слой',
        rule: 'Использовать SwiftUI. Не предлагать Flutter или UIKit.'
      }
    ]
  }
}
```

Инварианты намеренно не имеют категорий или приоритетов: каждое правило
одинаково обязательно. Их нельзя менять обычным сообщением пользователю — для
этого нужно обновить конфигурацию агента.

## Проверка запроса и ответа

При включённых инвариантах сервер использует независимого проверяющего с
ограниченным JSON-ответом.

1. **Pre-check** проверяет запрос пользователя. Если он прямо требует
   нарушение, основной агент не вызывается: пользователь получает правило,
   причину и совместимое направление.
2. Основной агент получает блок инвариантов в системном prompt после профиля и
   до task state, памяти и истории.
3. **Post-check** проверяет готовый текст ответа. Черновик не отображается до
   проверки.
4. При нарушении сервер отправляет основному агенту точные замечания и просит
   переписать полный ответ. Возможно не более двух исправлений, то есть трёх
   генераций всего. Если набор нарушенных правил повторяется, исправление
   прекращается раньше.
5. Если подходящий ответ не получен, проверка недоступна или вернула невалидный
   JSON, сервер блокирует результат вместо показа непроверенного текста.

Это не формальное доказательство для произвольного естественного языка:
семантическую оценку выполняет отдельный LLM-проверяющий. Сервер же
детерминированно контролирует его структуру, то, что проверены все активные
`id`, лимит попыток и запрет показа отклонённого черновика.

В результат добавляется метаинформация:

```ts
{
  status: 'passed' | 'repaired' | 'blocked',
  attempts: number,
  violatedInvariantIds: string[]
}
```

## API

Инварианты поддерживаются в обычных маршрутах создания и обновления агента:

```text
POST /api/agents
PUT  /api/agents/:agentId
```

Для независимого управления есть:

```text
GET /api/agents/:agentId/invariants
PUT /api/agents/:agentId/invariants
```

`PUT` принимает только обёртку из конфигурации агента:

```json
{ "invariants": { "enabled": true, "items": [] } }
```

## Совместимость

- Профиль управляет стилем, но не может отменить инвариант.
- Memory layers и context strategy получают только уже проверенный ответ;
  отклонённые черновики не сохраняются в short-term, working или long-term
  memory.
- В state machine pre-check выполняется до перехода `validation → execution`.
  Поэтому конфликтная правка остаётся на validation и не запускает доработку.
- Внутренние execution-вызовы также проходят проверку.
- Для агента с активными инвариантами streaming буферизуется до post-check;
  для остальных агентов потоковый вывод не меняется.
