# День 13. Конечный автомат задачи

Актуальная, более строгая версия управления переходами описана в
[`day-15.md`](day-15.md): она заменяет текстовые триггеры семантическим
классификатором и убирает ручной API для смены этапа.

Экран «Состояние задачи» запускает задачу обычным первым сообщением. Агент
возвращает структурированное решение, а сервер после проверки обновляет этап,
текущий шаг и ожидаемое действие. Состояние передаётся в системное сообщение на
каждом запросе, поэтому после паузы агент продолжает с сохранённого шага.

`expectedActor` устраняет неоднозначность: на `planning` и `validation`
ожидается действие пользователя, а на `execution` — действие агента. Когда
задача переходит в `execution`, сервер выполняет до четырёх внутренних
continuation-шагов подряд. Агент сам доводит результат до `validation`; только
там пользователь принимает работу или возвращает её на доработку.

## Состояние

```ts
{
  id: string,
  task: string,
  stage: 'planning' | 'execution' | 'validation' | 'done',
  status: 'active' | 'paused',
  currentStep: string,
  expectedAction: string,
  expectedActor: 'agent' | 'user',
  completedSteps: string[],
  updatedAt: string
}
```

Сервер разрешает только такие переходы:

```text
planning → execution → validation → done
                    ↖───────────┘
                    доработка при ошибке
```

`done` — конечное состояние. Пользователь утверждает план на `planning`, а
готовый результат — на `validation`. Из `validation` можно вернуться в
`execution`, если проверка выявила ошибку. В статусе `paused` нельзя отправить
сообщение агенту или сменить этап; сперва требуется действие `resume`. Пауза
доступна на любом незавершённом этапе и не очищает историю или состояние.

## API

Новые маршруты расположены рядом с общим API агентов:

```text
GET  /api/agents/:agentId/task-state
POST /api/agents/:agentId/task-state
DELETE /api/agents/:agentId/task-state
```

На экране не нужно вызывать `start` вручную: первое обычное сообщение создаёт
`planning` и сразу отправляется агенту для составления плана. Внешний `start`
тоже создаёт только `planning`; выбрать произвольный этап через API нельзя.

`POST` получает одно из действий:

```json
{ "action": "pause" }
```

```json
{ "action": "resume" }
```

Для создания новой задачи используется `start`, которому нужны `task`,
`currentStep` и `expectedAction`. `update` меняет только два последних поля,
не меняя этап. Ручные действия `advance` и `return-to-execution` удалены:
этап меняется исключительно через проверенный диалоговый жизненный цикл.

`DELETE /task-state` отменяет текущую задачу: удаляет её task-scoped историю,
сбрасывает рабочую память и возвращает экран к старту. Профиль, глобальная и
долгосрочная память агента при этом сохраняются. В интерфейсе действие требует
подтверждения.

## Что получает модель

`server/task-state.ts` собирает блок:

```text
ФОРМАЛЬНОЕ СОСТОЯНИЕ ЗАДАЧИ
Задача: …
Этап: …
Статус: …
Текущий шаг: …
Ожидаемое действие: …
```

Он добавляется после базового системного prompt (и после персонализации, если
она настроена), но до истории и нового сообщения. Агенту явно запрещено
повторять уже завершённые объяснения и предписано продолжать с `currentStep`.

В ответ модель возвращает только структуру:

```json
{
  "answer": "Текст для пользователя",
  "nextStage": "execution",
  "currentStep": "Реализовать согласованный план",
  "expectedAction": "Проверить результат"
}
```

Сервер показывает пользователю только `answer`. После утверждения плана первое
сообщение кратко объявляет переход, а сервер автоматически выполняет внутренние
шаги `execution` до перехода в `validation`. `nextStage` применяется лишь
после проверки графа переходов. Детали семантического подтверждения и отказа
на запрещённые переходы описаны в Day 15.

## Совместимость с предыдущими днями

У каждой задачи есть собственный `taskId`. Из него строится идентификатор
контекста для истории и выбранной context strategy, поэтому summary, sticky
facts и ветки одной задачи не попадают в другую. При создании новой задачи
сбрасываются её short-term history, context strategy и working memory.

Профиль пользователя, его global long-term memory и long-term memory агента не
сбрасываются: они относятся к пользователю или агенту, а не к конкретной
задаче. Учебный агент Дня 13 по умолчанию использует профиль iOS-разработчика,
summary strategy и automatic memory layers, то есть эти механизмы работают в одном
запросе с task state.

## Проверка

1. Отправьте вопрос в одном из этапов и убедитесь, что ответ опирается на шаг.
2. Нажмите «Поставить на паузу» на planning, execution или validation.
3. Убедитесь, что поле сообщения и переходы заблокированы.
4. Нажмите «Продолжить задачу», затем отправьте следующий вопрос: история и
   текущий шаг сохранятся.
5. Полный сценарий проверки недопустимых переходов приведён в Day 15.
